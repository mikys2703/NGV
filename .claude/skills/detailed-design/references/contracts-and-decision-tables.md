# 함수 계약, 알고리즘, 정책 의사결정표, API 계약

이 스킬이 만드는 상세설계에서 "핵심"이라고 표시된 함수/알고리즘/정책은 서술형 문장이 아니라 아래 형식 중 하나로 표현되어야 합니다. 문장으로만 설명하고 표/의사코드가 없다면 미완성입니다.

## 함수 계약 (템플릿 5장)

`architecture-design` 스킬의 `interface-contract.md`가 컴포넌트 경계의 계약이라면, 이것은 함수/메서드 하나하나의 계약(Design by Contract)입니다.

| 필드 | 내용 |
|---|---|
| 함수 ID/이름 | 모듈 분해(2장)의 단위 ID와 연결 |
| 입력 | 파라미터명, 타입, 유효 범위 |
| 출력 | 반환값, 타입, 의미 |
| 사전조건(precondition) | 호출 전에 성립해야 하는 것 — 호출자의 책임 |
| 사후조건(postcondition) | 정상 반환 시 보장되는 것 — 이 함수의 책임 |
| 부작용(side effect) | 인자로 받은 가변 객체 수정, 전역/외부 상태 변경 여부 |
| 예외/오류 | 어떤 조건에서 어떤 예외/오류를 발생시키는가 |
| 시간 제약 | 있다면 최대 실행시간 등 |

## 핵심 알고리즘 (템플릿 6장) — 의사코드 또는 흐름도

자연어 설명 대신 처리 순서를 번호가 매겨진 단계 또는 흐름도로 표현하고, 판단 조건과 경계값(최소/최대/0/음수/빈 입력 등)을 명시적으로 다루세요. 경계값을 언급하지 않은 알고리즘은 나중에 단위시험(SWE.4)에서 경계값 분석 기법을 적용할 근거가 없다는 뜻입니다.

```
알고리즘: 도어락_판정(속도, 도어상태, 충돌신호)
1. IF 충돌신호 == True: RETURN 즉시잠금해제  # 안전 최우선 분기
2. IF 속도 >= 임계속도(예: 20km/h) AND 모든_도어_닫힘(도어상태):
     RETURN 잠금
3. IF 속도 < 임계속도 AND 사용자_해제요청:
     RETURN 잠금해제
4. ELSE: RETURN 현재상태_유지
경계값: 속도 == 임계속도(경계), 도어상태 일부만 닫힘, 충돌신호와 해제요청 동시 발생(우선순위는 정책 의사결정표 참고)
```

## 정책 의사결정표 (템플릿 7장)

입력 조건 조합이 3개 이상 얽히거나, 조건 간 우선순위/충돌 해결이 필요한 정책은 의사결정표로 표현하세요. 표 형식 자체가 "빠진 조합이 없는가"를 눈으로 확인할 수 있게 해줍니다.

| 충돌신호 | 속도≥임계 | 사용자 해제요청 | 기대 동작 | 비고(충돌 해결 규칙) |
|---|---|---|---|---|
| True | - | - | 즉시 잠금해제 | 안전 최우선 — 다른 조건 무시 |
| False | True | False | 잠금 | |
| False | True | True | 잠금 유지 | 주행 중 해제요청은 무시(안전 규칙) |
| False | False | True | 잠금해제 | |
| False | False | False | 현재상태 유지 | |

의사결정표를 만들고 나면 조건 조합 수(2^n)와 표의 행 수가 맞는지, 다루지 않은 조합이 "현재상태 유지" 같은 기본값으로 암묵 처리되고 있는지 확인하세요.

## API 계약 (템플릿 9장, Web/API가 있는 경우)

엔드포인트마다 아래를 정의합니다: 메서드+경로, 요청 스키마(필드/타입/필수여부/유효성 규칙), 응답 스키마(성공/실패 각각), 오류 코드와 각 코드의 의미, 인증/세션 요구사항, 보안 경계(입력 검증이 서버 어디서 이뤄지는가). 함수 계약과 마찬가지로 "정상 케이스만" 정의하고 오류 응답 스키마를 비워두지 마세요.

## 이 파일과 다른 산출물의 관계

여기서 정의한 경계값·의사결정표 조합·API 오류 케이스는 SWE.4 단위시험 설계(`TPL-SWE4-001`)와 SWE.5 통합시험(`TPL-SWE5-001`, "경계값·동등분할·의사결정표·상태전이" 기법)가 그대로 재사용할 입력입니다. 여기서 애매하게 남겨두면 그 문서들에서 처음부터 다시 분석해야 합니다.
