# ISO 26262 Part 6 정합성 — 소프트웨어 단위 설계 (Clause 8)

ISO 26262 Part 6 Clause 8(소프트웨어 단위 설계 및 구현)은 `architecture-design` 스킬이 다루는 Clause 7(아키텍처)의 한 단계 아래, 함수/모듈 수준의 설계 원칙을 다룹니다. 여기서도 ASIL은 이미 주어졌다는 전제이며, HARA/ASIL 산정은 다루지 않습니다.

## 표기법

단위 설계도 아키텍처와 마찬가지로 ASIL이 높을수록 준정형/정형 표기(의사코드, 상태머신, 결정표, UML)가 권고됩니다. 이 스킬이 6장(핵심 알고리즘)과 7장(정책 의사결정표)에서 자연어 서술만으로 끝내지 못하게 하는 이유가 이것입니다.

## 전통적 설계 원칙과 "구현 언어에 맞게 번역하기"

ISO 26262 Part 6 Clause 8이 흔히 언급하는 단위 설계 원칙은 원래 C/C++ 계열 임베디드 코드를 염두에 둔 것입니다: 하나의 진입점/하나의 종료점, 무조건 분기(goto) 제한, 포인터 사용 제한, ASIL C/D에서 동적 객체/변수 회피(또는 안전한 참조 기법), 인터럽트 사용 제한, 변수 초기화, 재귀 사용 제한, 전역 변수 제한. **이 프로젝트의 구현 언어는 Python이므로(`WP_Templates`의 SBOM 템플릿 참고), 이 원칙들을 글자 그대로 옮기지 말고 의도를 번역해서 적용하세요.**

| 원래 원칙(C 계열 기준) | Python 기준으로 번역한 의도 | 이 스킬에서의 확인 방법 |
|---|---|---|
| 하나의 진입점/종료점 | 함수 하나에 여러 개의 암묵적 종료 경로(예외로 인한 조기 종료 포함)가 난립하지 않게 | 함수 계약(사후조건)에 모든 종료 경로와 그 결과를 명시 |
| goto/무조건 분기 제한 | Python에는 goto가 없지만, 예외를 흐름 제어용으로 남용하지 않기 | 알고리즘 의사코드에서 예외는 "오류" 용도로만 사용했는지 확인 |
| 포인터 사용 제한 | 가변 객체의 공유 참조(alias)로 인한 의도치 않은 부작용 — 특히 리스트/딕셔너리를 여러 곳에서 참조·수정하는 패턴 | 함수 계약의 "부작용"란에 인자로 받은 가변 객체를 수정하는지 명시 |
| ASIL C/D에서 동적 메모리 회피 | Python은 항상 동적 할당·가비지 컬렉션을 쓰므로 문자 그대로 적용 불가 — 대신 메모리 사용량의 예측 가능성(무한정 커지는 캐시/리스트가 없는지), GC로 인한 타이밍 변동이 시간 제약(함수 계약의 시간 제약란)에 문제가 되는지 확인 | 자원/시간 제약이 중요한 함수는 공통 자료형(4장)에 메모리 상한/자료구조 크기 제약을 명시 |
| 인터럽트 사용 제한 | 이 프로젝트가 SW-only PC/SIL·Web 검증이라면 실제 인터럽트 컨텍스트가 아닐 가능성이 높음 — 대신 비동기/콜백/이벤트 핸들러의 재진입성(reentrancy) 문제로 치환해서 검토 | 이벤트/콜백 기반 코드가 있다면 재진입 안전성을 오류/방어 동작(10장)에 명시 |
| 재귀 사용 제한 | 그대로 유효 — 입력에 따라 재귀 깊이가 커질 수 있는 알고리즘은 경계값과 종료조건을 명시 | 핵심 알고리즘(6장)에 재귀 종료조건과 최대 깊이(있다면) 명시 |
| 전역 변수 제한 | 그대로 유효, Python에서는 모듈 전역 상태·싱글턴 패턴이 흔한 함정 | 공통 결합(architecture-design의 `solid-coupling-cohesion.md`) 기준으로 모듈 전역 상태 사용을 점검 |

구현 언어가 다른 것으로 바뀌면(C/C++ 등) 이 표를 다시 원래 원칙 그대로 적용하면 됩니다 — 언어가 확인되지 않았다면 사용자에게 물어보세요.

## 오류 검출과 방어 동작 (템플릿 10장)

Clause 8은 단위 수준에서도 오류 처리 메커니즘(입력 유효성 검사, 범위 검사, 예외 처리, 자원 실패 대응)을 요구합니다. `architecture-design` 스킬의 오류 격리 원칙(9장, 전파 차단)이 컴포넌트 경계에서의 책임이라면, 여기서는 함수 하나하나가 "받은 입력이 계약을 어겼을 때 무엇을 하는가"까지 구체화합니다.

## 검증 관점

이 문서(11장 코딩 및 검증 규칙)에서 정의한 코딩 표준·정적분석·커버리지 기준은 이후 실제 구현과 SWE.4 단위검증에서 그대로 측정 대상이 됩니다. 지킬 수 없는 기준(예: 도구가 없는 정적분석)을 적어놓지 말고, `requirements-analysis` 스킬의 "실행 가능성 판단" 원칙과 동일하게 실제로 적용 가능한 기준만 명시하세요.
