# 상세설계

아키텍처가 "무엇으로 나눌지"를 정했다면, 상세설계는 "그 안을 실제로 어떻게 구현할지"를 코드 작성자가 바로 옮길 수 있는 수준까지 구체화하는 작업입니다. 아키텍처 문서를 다시 쓰는 게 아니라, 그 아래 계층(모듈/함수/알고리즘/자료구조)을 다루는 것이 이 스킬의 범위입니다.

## 참조 파일

| 파일 | 언제 읽는가 |
|---|---|
| `references/template.md` | 항상 먼저 — 조직 상세설계서 양식(TPL-SWE3-001)의 실제 구조를 확인할 때 |
| `references/uml-call-diagram.md` | 구현 단위와 호출관계를 다이어그램으로 표현할 때 (TPL-SWE3-002 drawio 양식) |
| `references/aspice-swe3.md` | SWE.3 기본관행 대응을 확인할 때 |
| `references/iso26262-part6-unit-design.md` | ASIL이 부여된 단위를 설계하거나, 구현 언어에 맞는 안전 설계 원칙을 적용할 때 |
| `references/contracts-and-decision-tables.md` | 함수 계약, 알고리즘, 정책 의사결정표, API 계약을 작성할 때 |
| `references/traceability-unit.md` | 아키텍처-상세설계-코드-단위시험 추적성을 갱신할 때 |

## 작업 절차

1. **입력 확인.** 이 상세설계가 어느 아키텍처 요소(들)를 구체화하는 것인지 확인합니다(`architecture-design` 스킬 산출물이 있으면 그것을 입력으로 사용). 아키텍처가 없는 상태에서 상세설계를 지어내지 마세요 — 상세설계는 아키텍처의 하위 산출물입니다.

2. **모듈 분해.** 대상 아키텍처 요소를 구현 단위(모듈/클래스/함수 등)로 나눕니다. 각 단위에 ID, 책임, 예정 소스 위치를 부여합니다(템플릿 2장). 분해가 `architecture-design` 스킬의 응집도/결합도/SRP 기준을 단위 수준에서도 지키는지 확인하세요 — 아키텍처에서 지킨 원칙이 상세설계에서 깨지면 의미가 없습니다.

3. **호출관계와 데이터 흐름.** 함수/클래스 간 호출 순서와 의존 방향을 `references/uml-call-diagram.md` 형식으로 표현합니다(템플릿 3장). 의존 방향이 아키텍처에서 정의한 인터페이스 방향과 어긋나지 않는지 확인하세요 — 상세설계 단계에서 몰래 역방향 의존이 생기는 경우가 흔한 실수입니다.

4. **공통 자료형.** 여러 단위가 공유하는 데이터 구조, 열거형, 단위(unit)/범위, 불변조건, 직렬화 규칙을 정의합니다(템플릿 4장).

5. **함수 계약과 알고리즘.** `references/contracts-and-decision-tables.md`에 따라 핵심 함수마다 계약(입력/출력/사전조건/사후조건/부작용/예외/시간제약)을 쓰고, 핵심 알고리즘은 의사코드 또는 흐름도로, 조건 조합이 복잡한 정책은 의사결정표로 표현합니다(템플릿 5~7장). 자연어로만 서술하고 표/의사코드가 없는 "핵심" 알고리즘은 미완성으로 취급하세요.

6. **상태전이 상세.** 아키텍처에서 정의한 상태 머신을 실제 저장 위치·전이 함수·이벤트·가드·타이머·초기화 동작 수준까지 구체화합니다(템플릿 8장).

7. **Web/API 상세 (해당하는 경우).** 엔드포인트가 있다면 요청/응답 구조, 검증 규칙, 오류 코드, 세션, 보안 경계를 `references/contracts-and-decision-tables.md`의 API 계약 형식으로 정의합니다(템플릿 9장).

8. **오류와 방어 동작.** 유효하지 않은 입력, 예외, 자원 실패에 대한 검출·처리·기록·복구를 정의합니다(템플릿 10장). ASIL이 있는 단위는 `references/iso26262-part6-unit-design.md`의 원칙을 적용하세요.

9. **코딩 및 검증 규칙.** 이 설계를 구현할 때 따를 코딩 표준(구현 언어에 맞는 것 — `references/iso26262-part6-unit-design.md` 참고), 정적분석 도구, 단위검증·커버리지 기준, 리뷰 기준을 명시합니다(템플릿 11장). 외부 라이브러리/FOSS를 도입한다면 `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SBOM-001_...` 양식(ENG-SBOM-001)에 그 의존성을 등록하도록 안내하세요 — 이 스킬이 그 문서를 대신 채우지는 않지만, 누락되지 않게 짚어주는 것은 이 단계의 책임입니다.

10. **단위/요구사항 할당과 구현 경계.** 구현 단위를 아키텍처 요소·SW 요구사항·단위시험에 연결하고(템플릿 12장), 생성 코드/외부 라이브러리/플랫폼 종속부/구현하지 않는 범위를 명시합니다(템플릿 13장).

11. **추적성 갱신.** `references/traceability-unit.md`에 따라 조직 추적 매트릭스(ENG-TRC-001)의 Detailed Design/Code 열을 갱신합니다(템플릿 14장). 상위(아키텍처) 추적과 하위(단위시험) 추적이 둘 다 채워지는지 확인하세요.

12. **최종 자가 점검.**
    - 모든 "핵심" 함수/알고리즘/정책에 계약·의사코드·의사결정표가 있는가(서술형 문장만 있는 것은 없는가)?
    - 호출관계가 아키텍처의 의존 방향과 일치하는가(역방향 의존이 몰래 생기지 않았는가)?
    - ASIL이 있는 단위에 오류 검출/방어 동작이 빠짐없이 정의됐는가?
    - 구현 언어에 안 맞는 원칙(예: 가비지 컬렉션 언어에 "포인터 사용 제한"을 그대로 적용)을 기계적으로 베끼지 않고, 실제 언어에 맞게 번역했는가?
    - 모든 단위가 상위 요구사항/아키텍처 요소에 연결되고, 추적 매트릭스가 갱신됐는가?

## 하지 말아야 할 것

- 아키텍처 문서 내용을 그대로 옮겨 적지 마세요 — 상세설계는 그 아래 수준(함수/알고리즘/자료구조)을 다룹니다.
- "적절히 처리한다", "필요시 예외 처리" 같은 서술로 오류 처리를 얼버무리지 마세요 — 구체적인 검출 조건과 대응을 쓰세요.
- 구현 언어와 무관한 설계 원칙(C 계열의 포인터/goto/동적 메모리 제한 등)을 실제 구현 언어 확인 없이 그대로 적용하지 마세요.
