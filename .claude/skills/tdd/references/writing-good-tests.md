# 좋은 테스트 작성법

**이 문서를 읽어야 할 때:** 테스트를 새로 쓰거나 수정할 때, mock을 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

> [obra/superpowers](https://github.com/obra/superpowers) `test-driven-development` 스킬의 `writing-good-tests.md`를 이 프로젝트의 Python/unittest 관례에 맞춰 옮긴 것입니다.

## 개요

테스트는 특정한 하나의 고장(break)을 잡기 위해 존재합니다. 다음 두 원칙이 모든 것을 지배합니다.

```
1. 모든 테스트는 자신이 잡아내는 고장을 이름으로 설명할 수 있어야 한다
2. 모든 테스트는 실제 대상을 실행해야 한다
```

`references/red-green-refactor.md`의 Red-Green-Refactor를 엄격히 따르면 두 원칙은 자연스럽게 지켜집니다 — 실제 코드를 대상으로 먼저 작성해서 실패를 확인한 테스트는 이미 "실패할 수 있음"을 증명했고, 실제 의존성이 느리거나 외부적일 때만 mock을 쓸 자격을 얻습니다.

## 원칙 1: 잡아내는 고장을 이름으로 설명하라

테스트 본문을 쓰기 전에 먼저 답하세요: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그 변경은 버그인가, 설계 결정인가?** 테스트는 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계 조건, 깨진 계약 중 하나를 잡아낼 때만 존재할 가치가 있습니다.

**기대값은 독립적으로 도출하세요.** 리터럴 값과 손으로 검증한 픽스처를 사용하세요 — 리터럴 `want` 값을 쓰는 테이블 기반 테스트가 선호되는 형태입니다. 검증 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과합니다.

```python
# ❌ 거울 검증(mirror assertion): 같은 함수로 양쪽을 계산 — 항상 참
expected = buildSearchQuery(tag="urgent")
self.assertEqual(buildSearchQuery(tag="urgent"), expected)

# ✅ 손으로 도출한 리터럴 값
self.assertEqual(buildSearchQuery(tag="urgent"), 'tag:"urgent"')
```

**변화감지기(change detector)를 만들지 마세요.** 의도적인 결정(상수 값, 정확한 메시지 문구, 내부 구조)만 실패하게 만드는 테스트는 재설계 때마다 울리고 정작 버그에는 반응하지 않습니다. 결정 자체가 아니라 그 결정에 의존하는 동작을 테스트하세요 — `assertEqual(MAX_RETRIES, 5)`가 아니라 "호출이 실패하면 5번 재시도하고 6번째 시도는 일어나지 않는다"를 검증하세요.

**동작을 테스트하고, 텍스트를 테스트하지 마세요.** 스크립트/스킬/설정 파일에 특정 문자열이 들어있는지 검증하는 것은 "소스가 소스임"만 증명합니다. 스크립트는 통제된 입력으로 실행해 출력·부작용·종료 코드를 검증하세요. 에이전트에게 지시하는 문서는 그 문서를 소비하는 에이전트의 동작으로 검증하고, 사람을 위한 설명문(prose)은 테스트 대상이 아닙니다.

**여러분의 코드를 테스트하고, 프레임워크를 테스트하지 마세요.** 여러분의 코드가 경계에서 맺는 계약(등록하는 라우트, 만들어내는 쿼리, 생성하는 페이로드)을 테스트하세요. 상위 라이브러리의 동작은 그 라이브러리 관리자가 테스트할 몫입니다(전형적인 예: 여러분의 라우터가 등록된 핸들러를 호출하는지 검증하는 것 — 그건 프레임워크의 테스트지 여러분의 테스트가 아닙니다). 상위 라이브러리의 동작이 예상과 달라 놀랐다면, 그 가정을 명시하는 좁은 특성화(characterization) 테스트 하나만 작성하세요. 같은 경계 원칙이 코드 내부에도 적용됩니다 — 생성자, getter, 상수, 단순 위임은 값을 검증·정규화·기본값 지정·유도·강제하거나 부작용을 낼 때만 테스트할 가치가 있고, 그렇지 않다면 이들에 의존하는 첫 번째 소비자 결과를 검증하세요.

### 게이트 함수 (테스트 본문을 쓰기 전에)

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패하게 만들 프로덕션 코드 변경을 말할 수 있는가?

  말할 수 없다              → 관찰 가능한 동작을 기준으로 재설계
  "소스 텍스트가 바뀌면 실패" → 산출물을 실행해서 효과를 검증하도록 바꿈
  의도적 결정만 실패시킴     → 변화감지기다; 그 결정에 의존하는 동작을 테스트

  기대값이 검증 대상 코드 없이 도출됐는지 확인하라.
  검증 대상 코드/헬퍼의 로직을 재사용한다면:
    리터럴 값 또는 손으로 검증한 픽스처로 교체하라
```

## 원칙 2: 실제 대상을 실행하라

**mock은 그 자체로 검증 대상이 될 수 없습니다.** mock이 있으면 통과하고 없으면 실패하는 assert는 실제 컴포넌트에 대해 아무것도 말해주지 않습니다. 실제 컴포넌트의 동작을 검증하세요 — mock을 검증하고 있다면 mock을 풀거나 그 assert를 지우세요.

```python
# ✅ 실제 동작 검증
self.assertTrue(controller.isDoorLocked())

# ❌ mock의 존재만 검증
mockActuator.lockDoor.assert_called_once()  # 이것만 검증하면 실제 잠금 여부는 모름
```

**올바른 수준에서 mock 하세요.** 실제 메서드를 대체하기 전에 그 메서드의 모든 부작용을 파악하세요. 느리거나 외부적인 연산만 mock 하고, 테스트가 의존하는 나머지는 실제로 유지하세요. 확신이 없다면 먼저 실제 구현으로 테스트를 실행해 무엇이 실제로 일어나는지 관찰하세요.

```python
# ❌ mock이 중복 감지 로직이 읽는 설정 저장까지 함께 삼켜버림
with unittest.mock.patch("tool_catalog.discover_and_cache_tools", return_value=None):
    ...

# ✅ 느린 서버 기동만 mock 하고, 설정 저장은 실제로 유지
with unittest.mock.patch("mcp_server_manager.MCPServerManager"):
    ...
```

**더블(double)을 구체적으로 만드세요.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 assert 하세요 — 아무 값이나 받아주는 페이크는 아무것도 검증하지 않습니다. 각 분기(성공/오류/잘못된 입력)마다 별도의 픽스처나 스파이(spy)를 두어 잘못된 분기가 기대치를 만족시키지 못하게 하세요.

**mock 데이터를 실제와 완전히 동일하게 구성하세요.** 실제로 존재하는 구조를 전부(테스트가 읽는 필드만이 아니라) mock 하세요. 부분적인 mock은 하위 코드가 누락된 필드를 읽을 때 조용히 실패합니다 — 테스트는 통과하는데 실제 통합에서는 깨집니다.

**프로덕션 클래스는 프로덕션 메서드만 가집니다.** 테스트에만 필요한 정리(cleanup)는 테스트 유틸리티에 두고, 프로덕션 클래스의 `destroy()` 같은 메서드로 만들지 마세요. 자문하세요: 이 메서드가 테스트에서만 호출되는가? 이 클래스가 이 자원의 생명주기를 실제로 소유하는가? 답이 "아니오"라면 테스트 유틸리티로 옮기세요.

**복잡한 mock보다 실제 컴포넌트를 선호하세요.** mock 설정이 테스트 로직보다 커지거나, mock에 실제 컴포넌트가 가진 메서드가 빠져 있거나, mock이 바뀔 때마다 테스트가 깨진다면 실제 컴포넌트를 쓰는 통합 테스트로 전환하세요.

### 게이트 함수 (mock/헬퍼를 추가하기 전에)

```
mock이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하라; 테스트가 의존하는 것은 실제로 유지하고
  그 아래의 느리거나 외부적인 수준만 mock 하라.

  mock 응답은 실제 구조를 완전히 반영해야 한다.

  테스트에서만 호출되는 메서드는 테스트 유틸리티에 둔다(프로덕션 클래스 아님).

  mock 자체를 assert 하려는 중인가?
    mock을 풀거나 그 assert를 지워라.
```

## 테스트는 구현과 함께 완성된다

Red-Green-Refactor 사이클(실패하는 테스트 → 최소 구현 → 리팩토링)이 곧 "완료"의 정의입니다. 동작이 필요로 하는 테스트만, 그리고 그만큼만 만드세요 — 자명한 코드와 사람을 위한 설명문은 테스트가 필요 없고, 절차를 만족시키기 위해 쓴 테스트는 유지보수 비용만 영원히 남깁니다.

## 뮤테이션 점검 (Mutation Check)

테스트를 끝내기 전, 프로덕션 코드를 머릿속으로 변형(mutate)해 보세요. 현실적인 변형마다 최소 하나의 테스트가 실패해야 합니다.

- 잘못된 상수/인자
- 잘못된 분기 처리
- 누락된 상태 변경 또는 부작용
- 빈 값/기본값 반환
- 0, 빈 값, `None`, 권한 없음, 잘못된 형식 입력에 대한 검증 누락

어떤 변형도 잡아내지 못한다면, 그 동작은 보호되지 않고 있는 것이거나 테스트가 동어반복(tautology)인 것입니다.

## 빠른 참조

| 상황 | 해야 할 일 |
|---|---|
| 테스트를 쓸 때 | 잡아낼 고장을 이름으로 설명하라 — 결정이 아니라 버그 |
| 기대값을 만들 때 | 손으로 도출하라; 검증 대상 코드로 계산하지 마라 |
| 스크립트/문서를 테스트할 때 | 실행하거나 소비자를 통해 검증하라; 텍스트를 grep 하지 마라 |
| 외부 의존성을 테스트하려 할 때 | 우리 쪽 경계 계약을 테스트하라, 그들의 문서화된 동작이 아니라 |
| mock 요소에 assert 하려 할 때 | 실제 컴포넌트를 테스트하거나 mock을 풀어라 |
| 메서드를 mock 하려 할 때 | 부작용을 먼저 파악하고, 느리거나 외부적인 수준만 mock 하라 |
| mock 응답을 만들 때 | 실제 구조를 완전히 반영하라 |
| 테스트 전용 정리(cleanup)가 필요할 때 | 테스트 유틸리티에 둬라 |
| mock 설정이 비대해지는 것을 볼 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환하라 |
| 테스트 파일을 끝낼 때 | 뮤테이션 점검을 수행하라 |

## 경고 신호

- 준비(setup)와 assert가 같은 객체를 공유해 항상 같아지도록 보장한다
- 패닉/크래시/셀렉터 누락으로만 테스트가 실패할 수 있다
- 의도적인 변경마다 실패하고, 실수로 인한 고장에는 절대 반응하지 않는다
- 기대값이 반복문/빌더/헬퍼 뒤에 숨어 있다
- 테스트가 소스 텍스트를 grep 하거나, 제거된 심볼이 계속 없는지만 확인한다
- 프레임워크만 남아도 테스트가 여전히 통과할 것이다
- 커버리지를 위해 존재할 뿐, 부작용이나 결과를 검증하지 않는다
- `*-mock` 테스트 ID에 assert 하거나 mock을 제거하면 실패한다
- 어떤 메서드가 테스트 파일에서만 호출된다
- mock 설정이 테스트의 절반 이상을 차지하거나, mock이 왜 필요한지 설명할 수 없다
- "혹시 몰라서" mock을 걸고 있다
