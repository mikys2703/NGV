# Red-Green-Refactor 상세 절차와 unittest 관례

이 문서는 [obra/superpowers](https://github.com/obra/superpowers) `test-driven-development` 스킬의 핵심 규칙(철칙, 각 단계의 필수 검증, 흔한 합리화, 위험 신호)을 이 프로젝트의 Python/unittest 관례와 결합한 것입니다.

## 언제 TDD를 적용하는가

**항상 적용:**
- 새 기능 추가
- 버그 수정
- 리팩토링
- 동작 변경

**예외(사용자에게 먼저 확인):**
- 일회성 프로토타입
- 생성된 코드(코드 생성기 산출물)
- 설정 파일

"이번만 TDD를 건너뛰자"는 생각이 든다면 멈추세요. 그것은 합리화입니다.

## Red

- 테스트 파일: `test_<모듈명>.py`, `unittest.TestCase`를 상속하는 클래스로 작성합니다(클래스명은 Python 표준 관례인 PascalCase — CLAUDE.md의 camelCase 규칙은 "함수명, 변수명"에 대한 것이며 클래스명에는 적용하지 않습니다).
- 테스트 메서드명은 `test`로 시작하는 camelCase(`testXxxYyy`)로, 무엇을 검증하는지 이름만 보고 알 수 있게 씁니다(`test1`, `testCase2` 같은 이름 금지).
- 테스트 하나는 **하나의 행동**만 검증합니다. 여러 행동을 한 테스트 메서드에 몰아넣지 마세요(예: `testValidatesEmailAndDomain`처럼 이름에 "그리고"가 들어가면 분리 신호).
- 실제 코드를 대상으로 작성하세요(mock은 불가피할 때만 — `references/writing-good-tests.md` 참고).
- 모든 테스트 함수에는 `references/test-documentation.md` 형식의 Doxygen 목적 설명 + 기법 + 긍정/부정 케이스 여부를 답니다.

## Verify Red — 실패를 직접 확인 (필수, 절대 생략 금지)

테스트를 작성한 직후 반드시 실행하세요(`python -m unittest test_<모듈명>.py -v`). 다음을 확인합니다:

- 테스트가 **실패**하는가(에러가 아니라 실패인지도 구분 — `AssertionError`가 아니라 `ImportError`/`AttributeError`라면 아직 구현이 없어서인지 확인)
- 실패 메시지가 예상한 이유와 일치하는가
- 기능이 없어서 실패하는 것이지, 오타나 잘못 작성된 테스트 때문에 실패하는 것이 아닌가

"구현이 없으니 당연히 실패한다"고 실행 없이 넘어가지 마세요 — 실수로 테스트 자체가 항상 통과하도록 잘못 쓰인 경우를 이 단계에서 걸러냅니다.

## Green

- 테스트를 통과시키는 데 필요한 최소한의 코드만 씁니다. 아직 요구되지 않은 기능을 추가하거나, 다른 코드를 리팩토링하거나, 테스트 범위를 넘어서 개선하지 마세요.
- 명백히 잘못된 이름(1~2글자, snake_case)으로 시작하지는 마세요 — 하지만 완벽한 리팩토링은 다음 단계 몫입니다.

## Verify Green — 통과를 직접 확인 (필수, 절대 생략 금지)

모든 테스트(이번에 추가한 것 + 기존 테스트 전체)를 실행해 다음을 확인합니다:

- 방금 추가한 테스트가 통과하는가
- 회귀 없이 기존 테스트 전체가 통과하는가
- 출력이 깨끗한가(불필요한 오류/경고가 섞여 있지 않은가)

## Refactor

- 테스트가 계속 통과하는 상태를 유지하면서: 중복 코드 제거, 함수 분리(SRP), 변수/함수 이름 정리를 합니다. **새 동작을 추가하지 않습니다.**
- 이 단계 마지막에 `code-quality-gates` 스킬을 호출해 5가지 게이트(함수 라인수, 순환복잡도, 중복코드, 주석비율, 네이밍)를 실행합니다. 위반이 있으면 여기서 고치고, 고친 뒤 테스트를 다시 실행해 여전히 통과하는지 확인합니다.
- 리팩토링 중에 새로운 동작이 필요하다는 것을 깨달으면, 그건 리팩토링이 아니라 새 요구사항이므로 Red 단계로 돌아가 테스트부터 추가하세요.

## 파일/디렉토리 관례

- 테스트는 구현 모듈과 이름이 대응하는 별도 파일에 둡니다(`도어락.py` → `test_도어락.py` 또는 프로젝트의 실제 소스 경로 관례를 따름 — `detailed-design` 스킬의 13장 "구현 경계"에 소스 위치가 있다면 그것을 따르세요).
- 테스트는 `python -m unittest discover`로 전체 실행 가능해야 합니다 — 개별 실행만 되고 discover에 안 걸리는 파일/클래스 이름을 쓰지 마세요.

## 좋은 테스트 vs 나쁜 테스트

| 기준 | 좋은 예 | 나쁜 예 |
|---|---|---|
| 최소성 | 한 가지만 검증 | `testValidatesEmailAndDomain`처럼 여러 행동을 한 테스트에 몰아넣음 |
| 명확성 | 이름이 행동을 설명(`testRejectsNegativeSpeed`) | `test1`, `testCase2` |
| 의도 표현 | 원하는 API/동작을 그대로 보여줌 | 요구사항을 오히려 감춤 |

## 흔한 합리화 — 전부 경계해야 할 신호

| 변명 | 실제로는 |
|---|---|
| "너무 단순해서 테스트할 필요 없다" | 단순한 코드도 깨진다. 테스트는 30초면 쓴다. |
| "나중에 테스트를 쓰겠다" | 구현 후에 쓴 테스트는 바로 통과해버려서 아무것도 증명하지 못한다. |
| "이미 수동으로 확인했다" | 수동 테스트는 즉흥적이고 기록도, 재현성도 없다. |
| "몇 시간 들인 걸 지우는 건 낭비다" | 매몰비용 오류 — 검증 안 된 코드를 계속 갖고 있는 것이 진짜 낭비다. |
| "TDD는 나를 느리게 만든다" | TDD는 프로덕션 버그를 막는 실용적인 지름길이다. |

## 위험 신호 — 발견하면 멈추고 처음부터 다시

- 테스트보다 코드를 먼저 썼다
- 구현 이후에 테스트를 끼워 맞췄다
- 테스트가 작성하자마자 통과한다(Verify Red 생략)
- 테스트가 왜 실패했는지 설명할 수 없다
- 테스트를 "나중에" 추가했다
- "이번만 예외로" 라고 합리화하고 있다
- "참고용으로 남겨두자", "기존 코드에 맞춰 테스트를 쓰자"고 생각한다
- "이미 몇 시간 썼는데 지우는 게 아깝다"고 생각한다

**모두 다음을 의미합니다: 코드를 지우고 테스트부터 다시 시작하세요.** 사용자의 명시적 허락 없이 예외를 두지 마세요.

## 최종 규칙

```
프로덕션 코드 → 테스트가 존재했고, 그 테스트가 먼저 실패했다
그렇지 않다면 → TDD가 아니다
```

## 각 단계에서 스스로 확인할 것

- Red: 이 테스트가 실패하는 이유가 "아직 구현이 없어서"가 맞는가, 아니면 테스트 자체가 잘못됐는가?
- Green: 지금 추가한 코드가 정확히 이 테스트를 통과시키기 위한 것인가, 아니면 앞서가서 미래 기능까지 구현했는가?
- Refactor: 품질 게이트를 실제로 실행했는가, 아니면 "괜찮아 보인다"고 넘어갔는가?
