# 상세설계 → 테스트 케이스 도출

`detailed-design` 스킬이 만든 산출물(함수 계약, 핵심 알고리즘의 경계값, 정책 의사결정표)에는 이미 "무엇을 검증해야 하는가"가 들어 있습니다. 이걸 다시 분석하지 말고 기계적으로 테스트 케이스로 옮기세요.

## 함수 계약 → 테스트

함수 계약의 각 필드가 테스트 케이스로 그대로 변환됩니다. **기법**/**케이스** 열은 `references/test-documentation.md`에서 각 테스트 함수의 Doxygen `@details`에 그대로 적을 값입니다.

| 계약 필드 | 테스트로 변환 | 기법 | 케이스 |
|---|---|---|---|
| 사전조건 | 사전조건을 만족하는 정상 입력 테스트 | 동등분할법 | 긍정 |
| 사전조건 | 사전조건을 위반하는 입력에 대해 명시된 예외/오류가 발생하는지 테스트 | 오류추정법 | 부정 |
| 사후조건 | 정상 입력에 대해 반환값/상태가 사후조건을 만족하는지 확인하는 assert | 동등분할법 | 긍정 |
| 부작용 | 가변 인자가 실제로 계약대로 수정되는지(또는 수정되지 않아야 한다면 그것도) 확인 | 동등분할법 | 긍정 |
| 예외/오류 | 각 예외 조건마다 별도 테스트 메서드로 `assertRaises` | 오류추정법 | 부정 |
| 시간 제약 | 정확한 타이밍 측정은 이 스킬의 단위 테스트 범위를 벗어날 수 있음 — 있다면 `time` 측정으로 근사 테스트를 만들거나, 통합/성능 시험(SWE.5/6) 몫임을 명시 | — | — |

## 경계값 → 테스트

핵심 알고리즘에 명시된 경계값(최소/최대/0/음수/빈 입력 등) 하나마다 테스트 메서드를 하나씩 만듭니다. "경계값 근처 3개(경계-1, 경계, 경계+1)"를 각각 별도 테스트로 만들면 놓치는 경우가 줄어듭니다. 기법은 **경계값분석**이며, 케이스는 그 값이 유효 범위 안이면 긍정, 범위를 벗어나면 부정입니다.

## 정책 의사결정표 → 테스트

의사결정표의 **모든 행**이 각각 하나의 테스트 메서드가 됩니다 — 표에 5행이 있으면 테스트도 최소 5개입니다. 이렇게 하면 표에서 빠진 조합이 있었는지(테스트를 만들다가 발견하는 경우가 많음) 자연스럽게 검증됩니다. 기법은 **의사결정표기반테스트**이며, 케이스는 그 행의 기대 결과가 정상 동작이면 긍정, 거부/예외/차단이면 부정입니다.

## 예시

상세설계의 의사결정표(도어락 판정)를 기준으로:

```python
import unittest

class TestDoorLockDecision(unittest.TestCase):
    def testLocksWhenSpeedAboveThresholdAndAllDoorsClosed(self):
        """!
        @brief 속도가 임계값을 넘고 모든 도어가 닫혀 있으면 잠금 상태로 판정되는지 검증한다.
        @details 기법: 의사결정표기반테스트(표 2번째 행) | 케이스: 긍정
        """
        ...

    def testKeepsLockedWhenReleaseRequestedWhileDrivingFast(self):
        """!
        @brief 주행 중 해제요청이 들어와도 안전 규칙에 따라 잠금이 유지되는지 검증한다.
        @details 기법: 의사결정표기반테스트(표 3번째 행) | 케이스: 부정
        """
        ...

    def testUnlocksImmediatelyOnCrashSignalRegardlessOfOtherConditions(self):
        """!
        @brief 충돌 신호가 있으면 다른 조건과 무관하게 즉시 해제되는지 검증한다.
        @details 기법: 의사결정표기반테스트(표 1번째 행, 안전 최우선 분기) | 케이스: 긍정
        """
        ...
```

메서드 이름은 이 프로젝트의 네이밍 규칙(camelCase, 3자 이상)을 따르되 `test`로 시작해야 unittest가 자동으로 찾습니다 — `testXxx` 형태는 camelCase이면서 동시에 unittest 탐색 조건(접두사 `test`)도 만족하므로 규칙 충돌이 없습니다. 각 테스트 함수의 Doxygen 문서화 규칙(형식, 기법명 목록)은 `references/test-documentation.md`를 따릅니다 — 예시 없이 생략하지 마세요.

## 상세설계 근거가 없을 때

테스트를 만들려는 함수에 대응하는 함수 계약/경계값/의사결정표가 상세설계 문서에 없다면, 테스트를 지어내지 말고 먼저 상세설계를 보완하거나(`detailed-design` 스킬) 사용자에게 확인하세요. 근거 없는 테스트는 "우연히 통과하는 구현"을 만들어낼 뿐입니다.
