# TDD (Red-Green-Refactor)

이 스킬은 "테스트를 나중에 끼워 맞추는" 방식이 아니라, 구현 코드 자체가 테스트를 통과하기 위해서만 존재하게 만드는 절차입니다. 테스트 없이 먼저 구현부터 쓰면 이 스킬을 따른 것이 아닙니다.

> 이 스킬은 [obra/superpowers](https://github.com/obra/superpowers)의 `test-driven-development` 스킬을 기반으로, 이 프로젝트의 상세설계 연동(`detailed-design` 스킬)과 품질 게이트(`code-quality-gates` 스킬), 그리고 테스트 문서화 규칙을 결합해 재구성한 것입니다.

## 이 스킬의 범위 (SWE.4) — 다른 테스트 수준과의 경계

이 스킬의 테스트 베이시스는 **상세설계의 함수 계약·경계값·의사결정표**이며, 검증 대상은 **함수/모듈 내부 로직**(화이트박스)입니다. 컴포넌트 간 인터페이스 상호작용 검증(그레이박스)은 `integration-testing` 스킬(SWE.5)의 몫이고, SW 요구사항 명세서 기준의 전체 소프트웨어 블랙박스 검증은 `sw-system-test` 스킬(SWE.6)의 몫입니다 — 이 스킬 안에서 그 두 가지를 대신 하려 하지 마세요. 세 스킬의 비교표는 `sw-system-test` 스킬의 `references/aspice-swe6.md`를 참고하세요.

## 철칙 (Iron Law)

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다.
```

**규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것입니다.** 테스트보다 먼저 구현 코드를 썼다면 그 코드는 삭제하고 처음부터 다시 시작하세요 — "참고용으로 남겨두기", "테스트를 쓰면서 그 코드에 맞추기", "일단 보고 베끼지 않기" 같은 절충은 전부 이 철칙을 어기는 것입니다. 테스트로부터 새로 구현하세요.

## 참조 파일

| 파일 | 언제 읽는가 |
|---|---|
| `references/test-case-derivation.md` | Red 단계에서 상세설계 산출물로부터 테스트 케이스와 기법(동등분할/경계값/의사결정표 등)을 도출할 때 |
| `references/red-green-refactor.md` | unittest 작성 관례, Red/Green/Refactor 각 단계에서 정확히 무엇을 검증해야 하는지, 그리고 흔한 합리화·위험 신호를 확인할 때 |
| `references/writing-good-tests.md` | 테스트가 실제로 버그를 잡는지(변화감지기가 아닌지) 확인하거나, mock을 추가하기 전에 반드시 확인할 때 |
| `references/test-documentation.md` | 테스트 함수에 기법·긍정/부정 케이스·Doxygen 목적 설명을 작성하는 정확한 형식을 확인할 때 (모든 테스트 함수에 필수) |

리팩토링 단계의 품질 기준(함수 라인수, 순환복잡도, 중복코드, 주석비율, 네이밍)은 이 스킬이 아니라 **`code-quality-gates` 스킬**이 담당합니다. Refactor 단계에서는 반드시 그 스킬을 호출하세요 — 기준을 이 스킬 안에서 다시 만들지 마세요.

## 작업 절차

1. **입력 확인.** 구현할 함수/단위의 상세설계 근거(함수 계약, 경계값, 정책 의사결정표 — `detailed-design` 스킬 산출물)를 확인합니다. 근거 없이 임의로 함수를 구현하지 마세요. 상세설계가 없다면 먼저 확인하거나 사용자에게 요청하세요.

2. **Red — 실패하는 테스트를 먼저 작성.** `references/test-case-derivation.md`에 따라 함수 계약의 사전/사후조건, 경계값, 의사결정표의 각 행을 unittest 테스트 케이스로 변환합니다. 각 테스트는 **하나의 행동만** 검증해야 하고, "이 테스트를 실패하게 만드는 프로덕션 코드 변경이 무엇인지" 스스로 답할 수 있어야 합니다(`references/writing-good-tests.md`의 Gate Function). 테스트 함수에는 `references/test-documentation.md` 형식대로 기법·긍정/부정 케이스·Doxygen 목적 설명을 작성합니다.

3. **Verify Red — 실패를 직접 확인.** **반드시 수행합니다.** 테스트를 실행해(`python -m unittest test_<모듈명>.py -v`) 다음을 확인하세요:
   - 테스트가 통과가 아니라 **실패**하는가
   - 실패 메시지가 예상한 이유(구현이 없거나 잘못됨)와 일치하는가 — 오타나 잘못된 테스트 자체 때문에 실패하는 것은 아닌가
   "구현이 없으니 당연히 실패한다"고 실행 없이 넘어가지 마세요.

4. **Green — 테스트를 통과시키는 최소 구현.** 지금 작성한 테스트를 통과하는 데 필요한 만큼만 구현합니다. 아직 요구되지 않은 기능을 미리 만들거나 과도하게 일반화하지 마세요(YAGNI). 다른 코드를 리팩토링하거나 개선하지 마세요 — 그것은 다음 단계입니다.

5. **Verify Green — 통과를 직접 확인.** **반드시 수행합니다.** 테스트를 실행해 다음을 확인하세요:
   - 방금 추가한 테스트가 통과하는가
   - 기존 테스트 전체가 회귀 없이 통과하는가
   - 출력에 경고/오류가 섞여 있지 않고 깨끗한가

6. **Refactor — 구조 개선 + 품질 게이트 통과.** 테스트를 계속 통과시키는 상태를 유지하면서 중복 제거, 이름 정리, 책임 분리를 합니다. 이 단계에서 새로운 동작을 추가하지 마세요 — 동작이 더 필요하다면 그것은 리팩토링이 아니라 새 요구사항이므로 2단계(Red)로 돌아가세요. 그다음 **`code-quality-gates` 스킬을 호출**해 함수 라인수·순환복잡도·중복코드·주석비율(Doxygen)·네이밍 규칙을 실제로 측정하세요. 게이트를 통과하지 못하면 다음 함수로 넘어가지 말고 이 자리에서 고치세요.

7. **반복.** 상세설계에서 식별된 다음 함수/시나리오/의사결정표 행으로 이동해 1~6을 반복합니다.

8. **완료 조건.** 상세설계의 "핵심" 함수와 의사결정표의 모든 행에 대응하는 테스트가 존재하고, 전부 통과하며, 각 테스트 함수가 `references/test-documentation.md` 형식을 갖췄고, `code-quality-gates`의 5가지 게이트를 모두 통과했을 때 이 단위의 구현이 끝난 것입니다.

## 위험 신호 — 발견하면 즉시 멈추고 다시 시작

- 테스트보다 구현 코드를 먼저 썼다
- 테스트를 구현 이후에 끼워 맞췄다
- 테스트가 작성하자마자 통과한다 (Verify Red를 건너뛴 것)
- 왜 테스트가 실패했는지 설명할 수 없다
- "이번만 예외로 TDD를 건너뛰자"고 합리화하고 있다
- "일단 참고용으로 남겨두자", "기존 코드에 맞춰 테스트를 쓰자"고 생각하고 있다
- "이미 몇 시간 썼는데 지우는 게 아깝다"고 생각하고 있다(매몰비용 오류 — 검증되지 않은 코드를 계속 갖고 있는 것이 진짜 손실입니다)

**위 항목에 해당하면 예외 없이: 코드를 지우고 테스트부터 다시 시작하세요.** 사용자(human partner)의 명시적 허락 없이는 예외를 두지 마세요.

## 하지 말아야 할 것

- 구현부터 쓰고 테스트를 나중에 맞춰 쓰지 마세요 — 그건 TDD가 아니라 사후 테스트 작성입니다.
- Red 단계에서 테스트를 실제로 실행해 실패를 확인하지 않고 다음 단계로 넘어가지 마세요.
- Green 단계에서 당장 필요하지 않은 기능까지 미리 구현하거나 다른 코드를 함께 리팩토링하지 마세요.
- Refactor 단계에서 품질 게이트를 건너뛰거나 "나중에 한꺼번에 검사"하지 마세요 — 함수 하나 끝날 때마다 확인합니다.
- 테스트가 검증 대상 코드(또는 그 헬퍼)로 기대값을 계산하게 하지 마세요 — 항상 통과하는 거울 검증(mirror assertion)이 됩니다.
- 느리거나 외부 의존적인 대상이 아닌데 습관적으로 mock을 걸지 마세요 — mock 자체의 존재를 검증하는 assert는 아무것도 증명하지 않습니다.
- 테스트 함수에 `references/test-documentation.md` 형식(기법/긍정·부정/Doxygen 목적)을 생략하지 마세요.
