# 양방향 추적성 방안

"추적 가능해야 한다"는 선언만으로는 추적성이 생기지 않습니다. 이 스킬은 요구사항을 만들 때마다 아래 규칙에 따라 ID를 부여하고 매트릭스를 갱신하는 것을 요구사항 작성 작업 자체의 일부로 취급합니다.

## ID 체계

레벨별 접두사 + 일련번호를 사용합니다. 프로젝트에 이미 다른 체계가 있다면 그것을 우선하고, 없다면 아래를 기본으로 사용하세요.

| 접두사 | 레벨 |
|---|---|
| `STK-REQ-####` | 이해관계자 요구사항 |
| `SYS-REQ-####` | 시스템 요구사항 |
| `SWE-REQ-####` | 소프트웨어 요구사항 |
| `ARC-####` | 아키텍처/설계 요소 (요구사항을 만족(satisfy)하는 대상) |
| `TC-####` | 테스트케이스/검증 산출물 |

ID는 한 번 부여되면 재사용하지 않습니다(요구사항이 삭제/폐기되어도 ID는 결번으로 남깁니다) — ID 재사용은 과거 추적 기록을 오염시킵니다.

## 추적 방향 — 반드시 양쪽 다

- **상위 추적(backward/upward)**: 이 요구사항이 어떤 상위 요구사항에서 파생(derive)됐는가? 왜 존재하는가?
- **하위 추적(forward/downward)**: 이 요구사항을 어떤 설계 요소가 만족(satisfy)하고, 어떤 테스트/분석이 검증(verify)하는가?

요구사항 작성 시점에는 하위 추적(설계/테스트)이 아직 존재하지 않을 수 있습니다. 그 경우 ID를 미리 채번해 "예정(TBD)"으로 표시하고, 실제 산출물이 생기면 그 즉시 매트릭스를 갱신하세요. 상위 추적 없이 만들어지는 요구사항은 원칙적으로 없어야 합니다 — 출처 없는 요구사항은 왜 필요한지 아무도 설명할 수 없습니다.

## 추적성 매트릭스 형식

요구사항 세트마다 아래 열을 가진 표(또는 CSV)를 함께 유지합니다. `references/template.md`가 자체 추적성 필드를 정의하고 있다면 그것을 우선하되, 최소한 아래 정보는 빠지지 않아야 합니다.

| ID | 유형 | 파생 출처(상위 ID) | 만족(satisfy) — 설계요소 | 검증(verify) — 테스트/분석 ID | ASIL | 상태 |
|---|---|---|---|---|---|---|
| SYS-REQ-0012 | 기능 | STK-REQ-0003 | ARC-0007 | TC-0045 | B | 초안 |
| SYS-REQ-0013 | 비기능(신뢰성) | STK-REQ-0003 | TBD | TC-0046(예정) | QM | 초안 |

## 유지 규칙

- 새 요구사항을 추가할 때마다 이 매트릭스에 행을 추가합니다 — 별도 작업으로 미루지 않습니다.
- 요구사항 문장을 수정하면(특히 의미가 바뀌는 수정이면), 그 요구사항을 만족/검증하는 하위 산출물이 여전히 유효한지 확인하고, 영향이 있으면 상태를 "재검토 필요"로 표시합니다.
- 상위 요구사항이 삭제/변경되면 그것을 파생한 하위 요구사항들을 매트릭스에서 역추적해 함께 검토합니다 — 이것이 양방향 추적성의 실질적인 목적입니다(한쪽만 되는 추적은 반쪽짜리입니다).
- SysML 요구사항 다이어그램(`references/uml-sysml.md`)을 함께 쓰는 경우, 다이어그램의 관계(deriveReqt/satisfy/verify)와 매트릭스 내용이 서로 어긋나지 않도록 동시에 갱신합니다.
