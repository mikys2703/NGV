# 명확성·일관성 확보 — EARS 문형

요구사항이 사람마다 다르게 해석되거나, 테스트로 옳고 그름을 판정할 수 없다면 그건 요구사항이 아니라 희망사항입니다. EARS(Easy Approach to Requirements Syntax)는 이 문제를 문장 구조로 강제하는 검증된 기법이며, 부수적으로 모든 요구사항의 문장 형태가 통일되어 일관성도 함께 확보됩니다.

## 기본 원칙

- 요구사항 하나에는 SHALL이 하나만 있어야 합니다(원자성). "그리고", "또한"으로 여러 동작을 묶지 마세요 — 나눠서 별도 ID를 부여합니다.
- 주어는 항상 명확한 시스템/구성요소명이어야 합니다("시스템", "그것" 같은 대명사 금지).
- SHALL = 반드시 만족해야 함(검증 대상). SHOULD = 권고사항(검증 대상 아님, 필요 시 별도 표시). MAY는 되도록 쓰지 않습니다 — 정말 선택사항이면 왜 요구사항 목록에 있는지 재검토하세요.
- "빠르게", "적절히", "충분히", "사용자 친화적으로" 같은 표현은 정량적 정의 없이 쓰지 않습니다. 반드시 숫자·조건으로 치환하세요.

## EARS 패턴 5가지

| 패턴 | 형태 | 언제 쓰는가 |
|---|---|---|
| 유비쿼터스(Ubiquitous) | THE `<시스템>` SHALL `<응답>` | 항상 성립하는 요구사항 (예: "THE 진단 모듈 SHALL 모든 오류 코드를 비휘발성 메모리에 저장한다") |
| 이벤트 기반(Event-driven) | WHEN `<트리거>`, THE `<시스템>` SHALL `<응답>` | 특정 사건 발생 시 |
| 상태 기반(State-driven) | WHILE `<상태>`, THE `<시스템>` SHALL `<응답>` | 특정 상태 동안 지속되는 동작 |
| 원치 않는 동작(Unwanted behavior) | IF `<원치 않는 조건/이벤트>`, THEN THE `<시스템>` SHALL `<응답>` | 오류/예외/고장 대응 (안전요구사항에서 특히 자주 사용) |
| 옵션 기능(Optional feature) | WHERE `<기능이 포함된 경우>`, THE `<시스템>` SHALL `<응답>` | 사양 옵션에 따라 달라지는 동작 |
| 복합(Complex) | 위 패턴들의 조합 (예: WHILE + WHEN, WHILE + IF) | 상태와 이벤트가 동시에 관여할 때 |

## 검증 가능성 자가 점검

문장을 쓴 뒤 다음을 스스로 확인하세요. 하나라도 "아니오"면 다시 씁니다.

1. 이 문장을 보고 통과/실패를 판정하는 테스트를 지금 바로 설계할 수 있는가?
2. 두 사람이 이 문장을 읽고 서로 다르게 해석할 여지가 있는 단어가 있는가? (있다면 정량화하거나 용어집에 정의를 추가)
3. SHALL이 두 개 이상 들어있지 않은가?
4. 이미 작성된 다른 요구사항과 같은 대상을 다른 이름으로 부르고 있지 않은가? (예: 어떤 곳은 "사용자", 다른 곳은 "운전자"라고 부르는 경우 — 같은 대상이면 용어를 통일)

## 용어집 유지

요구사항 세트마다 핵심 용어(시스템/구성요소명, 상태명, 행위자명)에 대한 짧은 용어집을 함께 유지하세요. 새 요구사항을 쓸 때 기존 용어집과 충돌하는 이름을 새로 만들지 말고, 용어집에 없는 새 용어가 필요하면 용어집에 추가부터 하세요. 이것이 일관성을 문장 단위가 아니라 요구사항 세트 전체 단위로 지키는 방법입니다.
