# 비기능 요구사항 — ISO/IEC 25010 + 실행 가능한 검증방안

비기능 요구사항(NFR)은 "빠르게", "안전하게", "유지보수하기 쉽게" 같은 말로 끝나는 순간 검증 불가능한 희망사항이 됩니다. 이 스킬에서는 모든 NFR을 (1) ISO/IEC 25010 품질특성에 명시적으로 매핑하고, (2) 정량적 수용기준을 부여하고, (3) 실제로 수행 가능한 검증방안을 함께 제시하는 것을 하나의 세트로 취급합니다.

## ISO/IEC 25010 품질특성 (제품 품질 모델)

| 특성 | 핵심 하위특성(예) | 전형적 NFR 예 |
|---|---|---|
| 기능 적합성(Functional Suitability) | 완전성, 정확성, 적절성 | 계산 결과의 허용 오차 범위 |
| 성능 효율성(Performance Efficiency) | 시간 반응성, 자원 사용성, 용량 | 응답시간, CPU/메모리 사용률, 최대 처리량 |
| 호환성(Compatibility) | 공존성, 상호운용성 | 타 ECU/프로토콜과의 동시 동작, 표준 프로토콜 준수 |
| 사용성(Usability) | 인식적합성, 학습성, 오류방지성, 접근성 | UI 조작 단계 수, 오조작 방지 확인창 |
| 신뢰성(Reliability) | 성숙성, 가용성, 결함허용성, 복구성 | MTBF, 가용률(%), 고장 후 복구시간 |
| 보안성(Security) | 기밀성, 무결성, 부인방지, 책임추적성, 인증성 | 인증 실패 시 잠금 정책, 통신 암호화 알고리즘/키 길이 |
| 유지보수성(Maintainability) | 모듈성, 재사용성, 분석성, 수정성, 시험성 | 결합도/순환복잡도 기준, 단위테스트 커버리지 |
| 이식성(Portability) | 적응성, 설치성, 대체성 | 지원 플랫폼/타깃 하드웨어 목록, 설치 소요시간 |

(ISO/IEC 25010:2023 개정판은 "안전성(Safety)"과 "유연성(Flexibility)"을 최상위 특성으로 추가하고 사용성을 "상호작용 역량(Interaction Capability)"으로 개편했습니다. 조직이 2011년판 8특성 체계를 쓰는지 2023년판을 쓰는지 불확실하면 사용자에게 확인하고, 확인 전에는 위 8특성 체계를 기본으로 사용하세요.)

## NFR 작성 절차

1. 요구사항이 어떤 품질특성(및 하위특성)에 해당하는지 명시적으로 태깅합니다. 여러 특성에 걸치면 주된 것 하나를 선택하고 나머지는 비고에 남깁니다.
2. EARS 문형으로 서술하되, NFR은 대부분 유비쿼터스 패턴("THE `<시스템>` SHALL `<정량기준>`을 만족한다")이거나 상태/이벤트 기반 패턴(부하 상황, 특정 조건 하에서의 성능 등)이 됩니다.
3. 수용기준은 숫자와 측정 조건을 함께 명시합니다. "빠르다" 대신 "몇 %ile 기준으로 몇 ms 이하, 어떤 부하 조건에서"까지 씁니다.
4. 검증방안을 아래 방법 중에서 고르고, **실제로 수행 가능한지** 확인합니다.

## 검증방안 4가지 유형과 선택 기준

| 방법 | 적합한 경우 | 예 |
|---|---|---|
| 테스트(Test) | 실행 중 동작을 직접 측정 가능 | 부하테스트, HIL 테스트, 침투테스트, 내구시험 |
| 분석(Analysis) | 실행 없이 계산/모델링으로 판단 가능 | 타이밍 분석, WCET 분석, 신뢰성 계산(FMEA 기반) |
| 검사(Inspection) | 산출물을 사람이 읽고 확인 | 코드 리뷰, 설계 리뷰, 정적분석 도구 결과 확인 |
| 시연(Demonstration) | 정해진 시나리오를 직접 보여줌으로써 확인 | 특정 조작 시퀀스를 시연해 UI 요구사항 충족 확인 |

## 실행 가능성 판단 — 반드시 지킬 것

검증방안을 쓰기 전에 스스로 물으세요: **"이 검증을 지금 이 프로젝트가 실제로 실행할 수 있는가?"**

- 필요한 도구/환경(부하생성기, HIL 랙, 보안 테스트 도구, 정적분석 도구 등)이 없거나 확인되지 않았다면, 그 방법을 그대로 적지 말고 다음 중 하나를 하세요:
  - 실제로 가능한 대체 방법으로 바꾼다(예: 침투테스트 대신 정적 보안분석 + 코드 리뷰).
  - 그 방법을 쓰려면 무엇이 선행되어야 하는지(도구 도입, 환경 구축)를 검증방안에 전제조건으로 명시한다.
- "품질보증팀이 검토한다", "추후 결정" 같은 방법은 검증방안이 아닙니다 — 누가, 무엇을 가지고, 무엇과 비교해서 통과/실패를 판정하는지가 드러나야 합니다.
- 하나의 요구사항에 검증방안을 여러 개 적어도 되지만(예: 분석 + 테스트로 교차 검증), 실행 불가능한 방법을 "일단 적어두고 보는" 식으로 끼워 넣지 마세요.

## 추적성과의 연결

검증방안에는 반드시 그 검증을 수행할 산출물의 ID(예: 테스트케이스 ID, 분석 리포트 ID)를 함께 적으세요. 아직 그 산출물이 없다면 ID를 미리 채번하고 "예정"으로 표시합니다 — 이것이 `references/traceability.md`에서 요구사항과 검증 산출물을 잇는 하위 방향 추적 링크가 됩니다.
