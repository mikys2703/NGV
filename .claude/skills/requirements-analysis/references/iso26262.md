# ISO 26262 정합성 — 안전 관련 요구사항

ISO 26262(자동차 기능안전)의 요구사항 관리 요건은 주로 Part 8 Clause 6(요구사항 관리)과, 요구사항이 도출되는 Part 3(컨셉 단계, HARA), Part 4(시스템), Part 6(소프트웨어)에서 나옵니다. 이 스킬이 다루는 것은 "안전요구사항을 어떻게 쓸 것인가"이며, HARA 수행이나 ASIL 산정 자체를 대신하지 않습니다 — ASIL이나 안전목표가 이미 주어졌다는 전제로 동작합니다. 주어지지 않았다면 사용자에게 확인하세요.

## 안전요구사항이 갖춰야 할 속성 (ISO 26262-8 Clause 6 기준)

요구사항 하나하나가 다음을 만족해야 합니다. 이는 이 스킬이 기본으로 요구하는 명확성·검증가능성 기준과 사실상 동일하며, 안전 관련 항목에서는 특히 엄격하게 적용됩니다.

- **명확(unambiguous)**: EARS 문형을 그대로 적용합니다.
- **이해 가능(comprehensible)**: 대상 독자(엔지니어, 검토자, 평가자)가 배경지식 없이도 읽을 수 있어야 합니다.
- **원자적(atomic)**: 하나의 요구사항 = 하나의 검증 가능한 진술.
- **내부적으로 일관(internally consistent)**: 같은 요구사항 세트 안에서 서로 모순되지 않음.
- **실현 가능(feasible)**: 현재 기술/아키텍처로 구현 가능해야 함. 불가능한 요구사항을 만들지 마세요.
- **검증 가능(verifiable)**: 정량적 수용기준과 실행 가능한 검증방안이 반드시 있어야 함(`references/iso25010-nfr.md`의 검증방안 원칙을 안전요구사항에도 동일하게 적용).

## ASIL 표기와 상속

- 안전 관련 요구사항에는 반드시 ASIL 등급(QM, A, B, C, D)을 명시합니다. 상위 요구사항(안전목표)의 ASIL을 그대로 상속하는 것이 기본이며, 달리 적용할 경우(ASIL 분해 등) 그 근거를 남깁니다.
- ASIL 분해(decomposition)를 적용해 하위 요구사항의 ASIL을 낮췄다면, 분해 근거(독립성 논증)를 요구사항 근거/출처 필드에 기록하세요. 근거 없이 ASIL을 임의로 낮추지 마세요.
- QM(안전 관련 아님)으로 분류되는 요구사항도 명시적으로 "ASIL: QM"이라고 표기합니다 — 표기를 생략해서 검토자가 안전 관련 여부를 추측하게 만들지 마세요.

## 자주 쓰이는 안전요구사항 패턴

원치 않는 동작(EARS의 IF-THEN) 패턴이 안전요구사항에서 특히 자주 쓰입니다 — 고장/이상 상태에 대한 시스템의 반응(안전 상태로 전이, 페일세이프 동작, 경고 등)을 기술하기 때문입니다.

```
IF 조향각 센서 신호가 유효 범위를 벗어나면(고장 감지), THEN THE 조향 제어 ECU SHALL 100ms 이내에 안전 상태(수동 조향 모드)로 전환한다.
```

## 추적성과의 연결

ISO 26262는 안전목표 → 기능안전요구사항 → 기술안전요구사항 → 하드웨어/소프트웨어 안전요구사항 → 검증 결과까지 양방향 추적을 명시적으로 요구합니다(Part 8 Clause 6). 이 스킬의 `references/traceability.md` 절차를 그대로 따르되, 안전 관련 요구사항은 추적 매트릭스에 ASIL 열을 반드시 포함시켜, 하위 요구사항이 상위 안전목표의 ASIL을 올바르게 상속/분해하고 있는지 한눈에 확인할 수 있게 하세요.

## 주의

이 참조 파일은 요구사항을 "쓰는" 방법을 다룹니다. HARA, 안전목표 도출, ASIL 산정, 안전 케이스(Safety Case) 작성 등은 별도의 전문 활동이며, 이 스킬의 범위가 아닙니다. 그런 입력이 없는 상태에서 안전요구사항 작성을 요청받으면, 안전목표/ASIL을 사용자에게 확인하고 임의로 만들어내지 마세요.
