# Automotive SPICE 4.1 정합성 — 요구사항 산출물

요구사항 작성이 걸리는 A-SPICE 프로세스는 주로 SYS.2(시스템 요구사항 분석)와 SWE.1(소프트웨어 요구사항 분석)입니다. 두 프로세스의 기본관행(Base Practice) 구조는 거의 동일하며, 이 스킬의 작업 절차는 그 구조를 그대로 반영합니다.

## SYS.2 / SWE.1 기본관행과 이 스킬의 대응

| 기본관행(요지) | 이 스킬에서의 대응 |
|---|---|
| BP1: 요구사항을 명세한다 | `references/ears-clarity.md` 문형으로 작성 |
| BP2: 요구사항을 구조화한다 | 기능/비기능, 상위 요구사항별로 그룹화하여 정리 |
| BP3: 요구사항을 분석한다(정확성, 기술적 타당성 등) | 작성 시 실현 가능성·모호성 여부를 자가 점검(`ears-clarity.md`의 자가 점검 목록) |
| BP4: 운영 환경에 미치는 영향을 분석한다 | 요구사항 근거/비고에 운영 환경 제약(예: 통신 대역폭, 기존 시스템과의 상호작용)이 있다면 명시 |
| BP5: 검증기준을 개발한다 | 모든 요구사항에 정량적 수용기준 + 실행 가능한 검증방안 필수 (`iso25010-nfr.md` 참고, 기능 요구사항도 동일 원칙 적용) |
| BP6: 일관성을 확보한다 | 작업 끝에 용어/ID/SHALL 사용 일관성 검토 수행 (SKILL.md 5-6단계) |
| BP7: 합의된 요구사항을 전달한다 | 산출물을 명확한 상태(초안/합의/기준선)로 표시해, 이해관계자가 "이건 아직 논의 중"과 "이건 합의됨"을 구분할 수 있게 함 |

## 이 스킬이 특히 신경 써야 할 A-SPICE 채점 포인트

실제 A-SPICE 평가에서 요구사항 산출물이 자주 지적받는 지점은 다음과 같습니다. 이 스킬로 만든 요구사항은 아래를 기본으로 만족해야 합니다.

- **검증기준(BP5) 누락** — "요구사항은 있는데 어떻게 검증할지가 없다"는 가장 흔한 지적입니다. 이 스킬은 검증방안을 선택 항목이 아니라 필수 필드로 취급합니다.
- **양방향 추적성 부재** — 상위(출처)만 있고 하위(어떤 설계/테스트로 검증됐는지)가 비어 있는 경우가 흔합니다. `references/traceability.md`의 매트릭스는 양쪽 방향을 모두 채우는 것을 전제로 합니다.
- **일관성 미확보(BP6)** — 같은 시스템을 여러 문서/작성자가 서로 다른 용어로 부르는 경우. `ears-clarity.md`의 용어집 유지로 대응합니다.
- **모호한 용어로 인한 검증 불가** — "충분히 빠르게" 같은 표현은 평가 시 "이 요구사항을 어떻게 검증했는지 보여달라"는 질문에 답할 수 없습니다.

## 안전 관련 요구사항과의 관계

ASIL이 부여된 요구사항을 다룰 때는 이 파일과 `references/iso26262.md`를 함께 적용합니다. A-SPICE의 BP5(검증기준)와 ISO 26262의 "검증 가능성" 요건은 사실상 같은 요구를 각자의 표준 언어로 말하고 있는 것이므로, 검증방안을 이중으로 따로 만들 필요는 없습니다 — 하나의 검증방안이 두 표준의 요구를 동시에 충족하도록 작성하세요.
