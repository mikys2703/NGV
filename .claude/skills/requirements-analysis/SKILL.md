# 요구사항 분석

자동차 임베디드/시스템 개발 맥락에서 ISO 26262와 Automotive SPICE 4.1을 동시에 만족하는 요구사항을 작성합니다. 요구사항 작성은 "문장을 그럴듯하게 다듬는 일"이 아니라 **하위 산출물(설계, 구현, 테스트)이 그대로 이어받아 쓸 수 있는 계약**을 만드는 일입니다. 모호하거나 검증 불가능한 요구사항은 산출물이 아니라 나중에 되돌아와야 하는 부채입니다.

## 참조 파일

작업 성격에 맞는 참조 파일을 필요할 때 읽으세요 (전부 한 번에 읽을 필요는 없습니다):

| 파일 | 언제 읽는가 |
|---|---|
| `references/template.md` | 항상 먼저 — 사용자가 제공한 템플릿(또는 임시 기본 양식)의 실제 구조를 확인할 때 |
| `references/ears-clarity.md` | 모든 요구사항 문장을 작성/검토할 때 (명확성·일관성의 핵심 기법) |
| `references/iso26262.md` | 안전 관련(ASIL 부여 대상) 요구사항을 다룰 때 |
| `references/aspice-requirements.md` | SYS.2/SWE.1 산출물 기대사항, 검증기준·일관성 확인을 다룰 때 |
| `references/uml-sysml.md` | 기능 요구사항을 다이어그램으로 표현할 때 |
| `references/iso25010-nfr.md` | 비기능 요구사항과 검증방안을 작성할 때 |
| `references/traceability.md` | 요구사항 ID를 부여하거나 추적성 매트릭스를 만들/갱신할 때 |

## 작업 절차

1. **템플릿 확인.** `references/template.md`를 읽습니다. 사용자가 아직 실제 템플릿을 주지 않았다면 그 파일에 명시된 임시 기본 양식을 쓰되, 반드시 "임시 양식이며 사용자 템플릿으로 교체 예정"이라고 사용자에게 알립니다. 실제 템플릿을 받으면 그 즉시 `references/template.md`를 갱신하세요 — 다음 작업부터는 그 템플릿이 기준입니다.

2. **범위와 출처 확인.** 이 요구사항이 어느 레벨(이해관계자/시스템/소프트웨어)인지, 상위 요구사항이나 입력 자료(컨셉 문서, HARA 결과, 상위 요구사항 목록 등)가 있는지 확인합니다. 없다면 사용자에게 묻고, 추측으로 상위 요구사항을 지어내지 마세요.

3. **요구사항 분류.** 각 요구사항을 기능/비기능으로 분류합니다.
   - **기능 요구사항** → `references/uml-sysml.md`에 따라 적절한 다이어그램(유스케이스/시퀀스/상태/액티비티/SysML 블록·요구사항 다이어그램)을 함께 작성합니다. 다이어그램 없이 텍스트만 있는 기능 요구사항은 미완성으로 취급하세요.
   - **비기능 요구사항** → `references/iso25010-nfr.md`에 따라 ISO/IEC 25010 품질특성에 매핑하고, 정량적 수용기준과 **실행 가능한** 검증방안을 함께 씁니다.
   - **안전 관련 요구사항**(ASIL이 부여되는 항목) → 추가로 `references/iso26262.md`를 따릅니다.

4. **문장 작성.** 모든 요구사항 문장은 `references/ears-clarity.md`의 EARS 패턴을 사용합니다. 하나의 요구사항에는 하나의 SHALL만 담습니다(원자성). 모호한 표현(빠르게, 적절히, 최대한 등)은 정량 기준 없이 쓰지 마세요.

5. **ID 부여 및 추적성 반영.** `references/traceability.md`의 ID 체계에 따라 고유 ID를 부여하고, 이번에 작성한 요구사항이 어떤 상위 요구사항에서 파생됐는지(derived from), 무엇으로 검증될 예정인지(to be verified by)를 추적성 매트릭스에 반영합니다. "추적 가능해야 한다"는 목표가 아니라, 이 스킬을 쓸 때마다 실제로 매트릭스를 갱신하는 행동입니다.

6. **일관성 검토.** 같은 작업 내에서(또는 기존 요구사항 목록이 주어졌다면 그것까지 포함해서) 용어·단위·ID 체계·SHALL/SHOULD 사용이 일관되는지 검토합니다. `references/aspice-requirements.md`의 BP.6(일관성 확보)에 해당하는 단계입니다.

## 산출물 형식

각 요구사항은 최소한 다음 속성을 가져야 합니다(정확한 표/필드명은 `references/template.md`를 따르되, 이 내용이 빠지면 안 됩니다):

- **ID** (`references/traceability.md`의 체계)
- **유형** (기능/비기능, 비기능이면 ISO 25010 품질특성)
- **문장** (EARS 패턴)
- **출처/상위 요구사항** (추적성 - 상위)
- **다이어그램** (기능 요구사항인 경우, `references/uml-sysml.md` 형식)
- **수용기준** (정량적)
- **검증방안** (실행 가능한 방법 + 어떤 산출물로 검증될지 - 추적성의 하위)
- **ASIL** (안전 관련인 경우만; QM이면 명시적으로 QM이라고 표기)
- **상태** (초안/합의/기준선 등)

## 하지 말아야 할 것

- 검증 방법을 실제로 수행할 수 없는데 그럴듯하게만 적지 마세요 (예: 보안 테스트 도구/환경이 없는 상황에서 "침투 테스트로 검증"이라고 쓰는 것). 실행 불가능하면 대안(정적분석, 코드 리뷰, 설계 검토 등 실제로 가능한 방법)을 제시하거나, 검증 수행에 필요한 선행조건을 명시하세요.
- 다이어그램을 텍스트 설명으로 때우지 마세요. 기능 요구사항이면 반드시 `references/uml-sysml.md` 형식의 다이어그램을 만드세요.
- 상위 요구사항이나 근거 없이 요구사항을 지어내지 마세요. 입력이 부족하면 사용자에게 묻거나, "가정"임을 명시하세요.
- 이미 만든 추적성 매트릭스를 갱신하지 않고 새 요구사항만 추가하지 마세요 — 추적성은 산출물이지 문서화 부채가 아닙니다.
