# Automotive SPICE 4.1 정합성 — SWE.5 소프트웨어 통합시험

## SWE.5 기본관행과 이 스킬의 대응

| 기본관행(요지) | 이 스킬에서의 대응 |
|---|---|
| BP1: 소프트웨어 통합시험 전략(회귀시험 전략 포함)을 개발한다 | SKILL.md 2·8단계, 템플릿 2·9장 |
| BP2: 소프트웨어 통합시험 명세를 개발한다 | SKILL.md 3·4단계, `test-case-derivation-integration.md`, 템플릿 6·7장, TPL-SWE5-002 |
| BP3: 소프트웨어 유닛을 소프트웨어 항목으로 통합한다 | SKILL.md 5단계 — 아키텍처 `integration-order.md`가 도출한 순서를 그대로 따름 |
| BP4: (회귀) 시험 케이스를 선정한다 | SKILL.md 8단계 |
| BP5: 통합된 소프트웨어를 시험하고 결과를 기록한다 | SKILL.md 5·7단계, TPL-SWE5-003 |
| BP6: 양방향 추적성을 확립한다 | SKILL.md 9단계, `traceability-integration.md` |
| BP7: 일관성을 확보한다 | SKILL.md 10단계(완료 조건 점검) |

(위 기본관행 목록은 Automotive SPICE 3.1/4.0/4.1에 걸쳐 안정적으로 유지되어 온 SWE.5 구조를 바탕으로 정리했습니다. 정확한 조항 번호와 문구는 조직이 보유한 라이선스 PAM 원문으로 검증하세요 — 이 스킬은 실무 적용을 돕는 것이지 공식 평가 기준을 대체하지 않습니다.)

## SWE.2와의 경계

통합 순서(BP3의 입력)와 인터페이스 계약은 `architecture-design` 스킬(SWE.2)이 이미 확정한 것을 그대로 이어받습니다. 통합시험 도중 인터페이스가 계약과 다르게 동작하거나 통합 순서가 실제로 불가능하다는 것이 밝혀지면, 이 스킬 안에서 조용히 우회하지 말고 아키텍처 산출물을 먼저 갱신해야 한다고 사용자에게 알리세요 — 그래야 추적성과 두 산출물의 정합성이 유지됩니다.

## SWE.4(단위검증)와의 경계

SWE.4는 함수/모듈 내부 로직을 검증하고(이 저장소에서는 `tdd`/`code-quality-gates` 스킬), SWE.5는 이미 개별적으로 검증된 유닛들이 인터페이스대로 상호작용하는지를 검증합니다. 내부 알고리즘이 옳은지 다시 확인하려 하지 마세요 — 그것은 이미 SWE.4에서 끝난 일이며, 이 스킬은 "경계를 넘는 상호작용"에만 집중합니다.

## SWE.6(시스템/자격시험)과의 경계

통합된 소프트웨어 전체가 **SW 요구사항 명세서**를 만족하는지 블랙박스로 검증하는 것은 이 스킬이 아니라 `sw-system-test` 스킬(SWE.6, `sw-system-tester` 서브에이전트)의 몫입니다(템플릿 12장 "적용 한계"에 그 경계를 명시). 이 스킬(SWE.5)은 **아키텍처의 인터페이스 계약**을 테스트 베이시스로 컴포넌트 경계를 그레이박스로 검증하고, `sw-system-test`는 **SW 요구사항 명세서**를 테스트 베이시스로 소프트웨어 전체를 블랙박스로 검증합니다 — 같은 결함이 양쪽에서 발견될 수 있어도 두 스킬이 서로의 테스트 베이시스를 대신 쓰지 않습니다. 세부 비교표는 `sw-system-test` 스킬의 `references/aspice-swe6.md`를 참고하세요. SW-only PC/SIL 검증 환경이라면 그 경계를 이 문서에도 정직하게 기록하세요.
