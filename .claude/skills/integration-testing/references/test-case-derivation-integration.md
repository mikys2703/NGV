# 아키텍처 → 통합시험 케이스 도출

`architecture-design` 스킬이 만든 산출물(인터페이스 계약 — 템플릿 6장, 통합 순서 — 템플릿 11장)에는 이미 "무엇을, 어떤 순서로 검증해야 하는가"가 들어 있습니다. 이걸 다시 분석하지 말고 기계적으로 TPL-SWE5-002의 행으로 옮기세요.

## 인터페이스 계약 → 테스트

인터페이스 계약(`architecture-design`의 `interface-contract.md`가 정의한 필드)의 각 필드가 통합시험 케이스로 그대로 변환됩니다.

| 계약 필드 | 테스트로 변환 | 기법(`iso26262-part6-integration-test.md`) |
|---|---|---|
| 오퍼레이션/시그널 | 정의된 호출/메시지가 실제로 제공자→사용자 간에 정확히 전달되는지 검증 | 인터페이스시험 |
| 데이터 계약(타입/단위/유효범위) | 유효 범위 내 데이터가 올바르게 전달·해석되는지(정상), 범위를 벗어난 데이터가 계약대로 거부/처리되는지(오류) | 인터페이스시험(정상) + 오류주입시험(범위 위반) |
| 사전조건/사후조건 | 호출 전 조건이 지켜졌을 때 사후조건이 실제로 성립하는지, 사전조건 위반 시 명시된 동작(오류 반환 등)이 일어나는지 | 요구사항기반시험 |
| 시간 제약 | 응답시간/타임아웃/주기가 목표 범위 내인지(근사 측정), 타임아웃 초과 시 정의된 복구 동작이 일어나는지 | 자원사용시험 |
| 오류 계약 | 실패 시 정의된 값/신호가 실제로 반환·전파되는지, 내부에서 흡수돼야 할 오류가 실제로 호출자에게 새어나가지 않는지(오류 전파 차단) | 오류주입시험 |

## 통합 순서 → 테스트 (단계적 통합)

통합 순서(`integration-order.md` 산출물)의 각 행을 순서대로 하나의 통합 단계로 취급합니다.

1. **해당 단계의 통합 항목**을 그 단계까지 이미 통합된 컴포넌트와 함께 실행합니다.
2. **"스텁/드라이버 필요"로 표시된 지점**은 아직 통합되지 않은 상위(드라이버)/하위(스텁) 컴포넌트를, 그 컴포넌트가 제공/요구하는 인터페이스 계약을 그대로 구현한 대역으로 대체합니다 — 계약과 다르게 단순화한 스텁/드라이버를 쓰면 이후 실제 컴포넌트로 교체했을 때 드러날 문제를 이 단계에서 놓치게 됩니다.
3. **각 단계마다 최소 하나의 통합시험 케이스**를 만들어, 이번에 새로 연결된 인터페이스가 이전 단계까지의 컴포넌트와 실제로 맞물리는지 검증합니다. 순서를 건너뛰고 마지막에 한꺼번에 시험하지 마세요 — 문제 발생 지점을 좁히기 위한 단계적 통합의 목적 자체가 무너집니다.
4. **비고(위험/불확실성)란에 표시된 항목**은 우선순위를 높여 먼저 시험합니다(위험 기반 우선순위).

## TPL-SWE5-002 행 작성 규칙

| 열 | 채우는 방법 |
|---|---|
| Test ID | 채번 규칙(예: `IT-<컴포넌트>-NNN`) |
| Trace | 검증 대상 인터페이스 ID(`IF-...`) + 통합 순번 — `traceability-integration.md` |
| Integration Item | 통합 순서 표의 "컴포넌트/통합 단위" 값 |
| Stimulus | 인터페이스 계약의 오퍼레이션/시그널·데이터 계약에서 도출한 구체적 입력값 |
| Expected Result | 인터페이스 계약의 사후조건/오류 계약에서 도출한 기대 결과 |
| Technique | 위 표에서 선택한 기법명 |
| Automation | 자동화된 통합시험 스크립트로 실행 가능하면 "자동", 수동 절차가 필요하면 "수동" |

## 자동화된 통합시험 스크립트를 작성할 때

Automation 열이 "자동"인 케이스를 Python `unittest` 스크립트로 구현한다면, `tdd` 스킬의 `references/test-documentation.md` 형식(`"""! @brief ... @details 기법: ... | 케이스: 긍정/부정 """`)을 그대로 재사용해 테스트 함수를 문서화하세요 — 이 스킬에서 별도 형식을 새로 만들지 않습니다. 이때 `기법`은 이 문서의 기법명(인터페이스시험/오류주입시험 등)을 쓰고, `케이스`는 정상 상호작용을 검증하면 긍정, 오류/거부/차단 동작을 검증하면 부정으로 표기합니다.

## 아키텍처 근거가 없을 때

검증하려는 통합 지점에 대응하는 인터페이스 계약이나 통합 순서 항목이 아키텍처 산출물에 없다면, 테스트를 지어내지 말고 먼저 아키텍처를 보완하거나(`architecture-design` 스킬) 사용자에게 확인하세요. 근거 없는 통합시험은 "우연히 통과하는 통합"을 만들어낼 뿐입니다.
