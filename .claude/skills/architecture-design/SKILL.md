# 아키텍처 설계

요구사항을 소프트웨어 구조로 바꾸는 작업입니다. 이 단계에서 내려진 결정(어떻게 나눌지, 무엇을 통해 통신하게 할지)은 이후 상세설계·구현·통합시험 전체의 비용을 결정합니다. 잘못된 결합은 나중에 리팩토링으로 고치는 것보다 지금 막는 것이 훨씬 쌉니다.

## 참조 파일

| 파일 | 언제 읽는가 |
|---|---|
| `references/template.md` | 항상 먼저 — 조직 아키텍처 설계서 양식(TPL-SWE2-001)의 실제 구조와 산출물 명명 규칙을 확인할 때 |
| `references/uml-diagram.md` | 논리 아키텍처/컴포넌트 다이어그램을 그릴 때 (TPL-SWE2-002 drawio 양식 기준) |
| `references/aspice-swe2.md` | SWE.2 기본관행 대응, 특히 아키텍처 대안 제시·평가 단계를 진행할 때 |
| `references/iso26262-part6.md` | ASIL이 부여된 요소를 다루거나 오류 격리/안전 동작을 설계할 때 |
| `references/solid-coupling-cohesion.md` | 컴포넌트 분해, 응집도/결합도, SOLID 준수를 검토할 때 |
| `references/interface-contract.md` | 컴포넌트 인터페이스를 정의할 때 (모든 통신은 인터페이스로만) |
| `references/integration-order.md` | 컴포넌트 통합 순서를 정할 때 |

## 작업 절차

1. **입력 확인.** 대상이 되는 요구사항 목록(가능하면 `requirements-analysis` 스킬로 만든 것), ASIL 컨텍스트(있다면), 조직 템플릿(`references/template.md`)을 확인합니다. 요구사항이 없는 상태에서 아키텍처를 지어내지 마세요 — 무엇을 만족시키기 위한 구조인지 먼저 확정합니다.

2. **설계 원칙 확정.** `references/solid-coupling-cohesion.md`와 `references/iso26262-part6.md`를 바탕으로 이번 설계에 적용할 원칙(분해 기준, 응집도/결합도 목표, 인터페이스 원칙, 오류 격리, 변경 용이성 확보 방법)을 먼저 문장으로 정리합니다. 이것이 템플릿 2장(아키텍처 설계 원칙)의 내용이 되고, 이후 모든 설계 결정의 판단 기준이 됩니다.

3. **아키텍처 대안 제시 및 사용자 선정 — 생략 금지.** 상세 설계로 바로 들어가지 말고, 요구사항과 품질속성(성능, 안전, 변경 용이성 등)에 맞는 서로 다른 구조 패턴 2~3개를 후보로 제시하세요(예: 계층형, 이벤트 기반/발행-구독, 포트-어댑터/헥사고날, 파이프-필터, 마이크로커널 등 — 상황에 맞는 것을 고르고 무관한 패턴을 억지로 끼워 넣지 마세요). 각 후보마다 장단점을 응집도/결합도, 변경 용이성, 성능, 안전 요구 충족 관점에서 비교하고, 실제 선택은 AskUserQuestion으로 사용자에게 맡기세요. 이 단계는 A-SPICE SWE.2의 "대안 아키텍처 평가" 기본관행에 대응합니다(`references/aspice-swe2.md`). 사용자가 이미 특정 구조를 지정했다면 생략 가능하지만, 그 경우에도 왜 그 구조가 적합한지 간단히 확인하세요.

4. **논리 아키텍처 상세화.** 선택된 구조를 컴포넌트/요소로 분해하고, 각 요소의 책임·입력·출력·상태·오류 처리를 정의합니다(템플릿 3~4장). 분해 결과가 2단계에서 정한 응집도/결합도 원칙을 지키는지 `references/solid-coupling-cohesion.md`의 점검 기준으로 확인하세요.

5. **인터페이스 정의 — 생략 금지.** 컴포넌트 간 통신 경로마다 `references/interface-contract.md`에 따라 인터페이스를 정의합니다. 컴포넌트가 다른 컴포넌트의 내부 상태/필드에 직접 접근하는 설계는 이 시점에 걸러내세요. 내부 인터페이스와 외부(하드웨어/통신/사용자) 인터페이스를 구분합니다(템플릿 6장).

6. **동적 동작과 상태 전이.** 주요 시나리오의 호출 순서(시퀀스)와 상태 의존 동작(상태 머신)을 `references/uml-diagram.md` 형식으로 표현합니다(템플릿 7~8장).

7. **오류 격리와 안전 동작.** ASIL이 있는 요소는 `references/iso26262-part6.md`의 오류 검출/전파 차단/안전 상태 전이 원칙을 적용해 설계합니다(템플릿 9장). ASIL이 없는(QM) 요소는 그렇다고 명시하세요.

8. **품질속성 분석.** 요구사항 단계에서 정의된 비기능 요구사항(있다면 ISO 25010 기반)이 이 구조로 어떻게 충족되는지 시나리오 기반으로 분석합니다(템플릿 10장).

9. **통합 순서 정의 — 생략 금지.** `references/integration-order.md`의 방법(의존성 그래프 기반 위상 정렬)으로 통합 단위와 순서를 도출하고, 스텁/드라이버가 필요한 지점을 표시합니다(템플릿 11장). 이는 이후 SWE.5 산출물(TPL-SWE5-001)의 입력이 됩니다.

10. **요구사항 할당과 추적성.** 각 요구사항을 담당 아키텍처 요소/인터페이스에 매핑하고(템플릿 12장), 조직 추적 매트릭스(ENG-TRC-001, 열 구성: Upper Req/SW Req/Architecture/Detailed Design/Code/SWE.4/SWE.5/SWE.6/Coverage)에 이번 아키텍처 요소를 반영합니다(템플릿 14장). 매핑 안 된 요구사항이나, 요구사항 없이 존재하는 아키텍처 요소(과잉 설계)가 있으면 짚어내세요.

11. **자원/배포 경계.** 실행 노드, 프로세스, 메모리/CPU 제약, 배포 제약을 정리합니다(템플릿 13장).

12. **최종 자가 점검.** 산출물을 내놓기 전에 다음을 스스로 확인하세요:
    - 모든 컴포넌트 간 통신이 정의된 인터페이스를 통해서만 이뤄지는가? (직접 참조/공유 상태 없음)
    - 응집도가 낮거나 결합도가 높은 컴포넌트가 남아있지 않은가?
    - SOLID 원칙 중 위반된 것이 있는가?
    - 통합 순서가 실제 의존성과 일치하는가(하위 의존성이 먼저 오는가)?
    - 모든 요구사항이 어딘가에 할당되었는가(양방향 추적)?

## 산출물

최종 산출물은 조직 템플릿(`references/template.md`)의 15개 절 구조를 그대로 따르는 문서 초안과, 그 안에 포함될 UML/SysML 다이어그램(`references/uml-diagram.md` 형식)입니다. 사용자가 실제 `.docx`/`.drawio` 파일로 채워달라고 요청하면 `docx` 스킬을 사용해 `WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-001_SW 아키텍처 설계서 템플릿.docx`를 기반으로 작성하고, 조직 명명 규칙(`ENG-SWE2-001_SW 아키텍처 설계서` 등)을 따르세요.

## 하지 말아야 할 것

- 후보 아키텍처 비교 없이 곧장 하나의 구조로 확정하지 마세요 (3단계는 필수입니다).
- 인터페이스 없이 컴포넌트가 서로의 내부를 직접 참조하게 하지 마세요.
- "느슨하게 결합되어 있다"처럼 근거 없이 선언만 하지 마세요 — `references/solid-coupling-cohesion.md`의 기준으로 실제로 확인하세요.
- 통합 순서를 감이나 구현 편의로 정하지 말고, 실제 의존성 그래프에서 도출하세요.
- 요구사항이나 조직 템플릿 없이 아키텍처를 지어내지 마세요.
