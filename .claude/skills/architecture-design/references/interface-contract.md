# 인터페이스 정의 — 컴포넌트 간 통신은 인터페이스로만

이 스킬이 만드는 아키텍처에서 컴포넌트 두 개가 서로 "알아야" 하는 유일한 방법은 정의된 인터페이스입니다. 한쪽이 다른 쪽의 내부 필드, 전역 변수, 구현 세부사항에 직접 접근하는 설계는 이 요건 위반이며, 발견 즉시 인터페이스로 감싸도록 재설계하세요(`references/solid-coupling-cohesion.md`의 내용 결합/공통 결합 금지와 같은 문제).

## 인터페이스 하나가 갖춰야 할 계약 요소

템플릿 6장(인터페이스 명세)의 "작성 안내"(인터페이스 ID, 제공자, 사용자, 데이터, 호출 조건, 시간 제약, 오류 계약)를 구체적인 필드로 풀면 다음과 같습니다.

| 필드 | 내용 |
|---|---|
| 인터페이스 ID | 고유 식별자 (예: `IF-DOORCTRL-001`) |
| 제공자 / 사용자 | 어느 컴포넌트가 제공(provided)하고, 어느 컴포넌트가 요구(required)하는가 — `references/uml-diagram.md`의 볼-소켓 표기와 일치시킬 것 |
| 오퍼레이션/시그널 | 함수 시그니처 또는 메시지/이벤트 정의 (이름, 파라미터, 반환/응답) |
| 데이터 계약 | 주고받는 데이터의 타입, 단위, 유효 범위 |
| 사전조건/사후조건 | 호출 전에 성립해야 하는 조건, 호출 후 보장되는 상태 (Design by Contract) |
| 시간 제약 | 응답시간, 타임아웃, 주기(있다면) — 비기능 요구사항(성능)과 연결 |
| 오류 계약 | 실패 시 무엇을 반환/신호하는가, 어떤 오류가 호출자에게 전파되고 어떤 것이 내부에서 흡수되는가 — `references/iso26262-part6.md`의 전파 차단과 직결 |
| 내부/외부 구분 | 소프트웨어 요소 간(내부, 6.1절) vs 하드웨어/통신/사용자/외부서비스(외부, 6.2절) |

## 인터페이스 설계 시 자가 점검

1. 이 연결에 실제로 정의된 인터페이스가 있는가, 아니면 구현하면서 슬쩍 직접 참조하게 될 위험이 있는가?
2. 이 인터페이스가 노출하는 오퍼레이션이 사용자(호출하는 컴포넌트) 입장에서 실제로 다 필요한가, 아니면 ISP(인터페이스 분리) 위반으로 더 잘게 나눠야 하는가?
3. 상위 컴포넌트가 이 인터페이스의 구체 구현이 아니라 추상 정의에 의존하도록 되어 있는가(DIP)? 그래야 구현체를 통합시험에서 스텁/드라이버로 바꿔 끼울 수 있습니다(`references/integration-order.md`).
4. 오류 계약이 없는 인터페이스는 없는가? "정상 동작"만 정의하고 실패 시나리오를 비워두면 9장(오류 격리)과 통합시험 설계 모두에서 구멍이 됩니다.

## 산출물과의 연결

정의한 인터페이스는 템플릿 6장 표에 그대로 반영하고, `references/uml-diagram.md`의 다이어그램에도 동일한 ID/이름으로 표시하세요. 인터페이스 ID는 추적성 매트릭스(템플릿 14장, ENG-TRC-001)에서 "Architecture" 열의 세부 항목으로도 쓰일 수 있으니, 이후 상세설계·통합시험 단계에서 재사용할 수 있도록 임의로 이름을 바꾸지 마세요.
