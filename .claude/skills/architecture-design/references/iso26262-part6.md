# ISO 26262 Part 6 정합성 — 소프트웨어 아키텍처 설계

ISO 26262 Part 6(소프트웨어 수준 제품 개발)의 소프트웨어 아키텍처 설계 관련 요건은 주로 Clause 7(소프트웨어 아키텍처 설계)에서 나옵니다. 이 참조 파일은 그 요건을 이 스킬의 작업 절차에 매핑합니다. HARA/ASIL 산정 자체는 다루지 않습니다 — ASIL은 요구사항 단계에서 이미 주어졌다는 전제입니다.

## 표기법(Notation) — 왜 UML/SysML을 쓰는가

ISO 26262 Part 6은 아키텍처를 비정형(자연어), 준정형(semi-formal, 예: UML/SysML), 정형(formal) 표기법 중에서 ASIL에 맞게 선택하도록 요구합니다. ASIL이 높아질수록(특히 C/D) 모호함이 적은 준정형·정형 표기가 강하게 권고됩니다. 이 스킬이 UML/SysML 다이어그램(`references/uml-diagram.md`)을 모든 기능 요소에 필수로 요구하는 이유가 이것입니다 — QM/ASIL A 요소라도 준정형 표기를 기본으로 쓰고, 자연어만으로 대체하지 마세요.

## 아키텍처 설계 원칙 — 사용자가 요청한 항목과의 직접 대응

ISO 26262 Part 6은 소프트웨어 아키텍처가 지켜야 할 설계 원칙을 제시합니다. 다음은 이 스킬이 반드시 확인하는 원칙이며, 사용자가 요청한 "높은 응집력/낮은 결합도"와 정확히 대응합니다.

| 원칙 | 이 스킬에서의 확인 방법 |
|---|---|
| 적절한 계층 구조(hierarchical structure) | 논리 아키텍처(템플릿 3장)가 과도하게 평평하거나 과도하게 깊지 않은지 확인 |
| 컴포넌트 크기 제한 | 하나의 컴포넌트가 너무 많은 책임을 갖지 않는지 (`solid-coupling-cohesion.md`의 SRP와 연결) |
| **높은 응집력(high cohesion)** | `references/solid-coupling-cohesion.md`의 응집도 분류로 각 컴포넌트를 점검 |
| **낮은 결합도(low coupling)** | `references/solid-coupling-cohesion.md`의 결합도 분류로 컴포넌트 간 연결을 점검 |
| 인터페이스 크기 제한 | 인터페이스 하나가 너무 많은 기능을 한 번에 노출하지 않는지 (`interface-contract.md`) |
| 필요 이상의 가변성 배제 | 당장 필요 없는 확장 포인트를 미리 만들지 않기 — SOLID의 OCP는 "예측"이 아니라 "실제 변경 축"에 대해서만 적용 |
| 인터럽트/포인터 사용 제한, ASIL C/D에서 동적 객체 회피(또는 안전한 참조 기법 사용) | 상세설계·구현 단계의 관심사이지만, 아키텍처에서 이런 메커니즘에 의존하는 설계를 만들었다면 그 사실과 대응 방안을 9장(오류 격리)에 남길 것 |

(정확한 원칙 목록과 조항 번호는 ISO 26262 판(2011/2018)에 따라 다소 다르게 조직되어 있습니다. 이 표는 공개적으로 널리 알려진 표준 구조를 요약한 것이며, 공식 인증/심사에는 조직이 보유한 정식 표준 문서를 대조하세요.)

## 오류 검출·전파 차단·안전 상태 (템플릿 9장)

ASIL이 부여된 요소는 다음을 아키텍처 수준에서 명시해야 합니다:

- **오류 검출**: 어디서(어느 컴포넌트/인터페이스에서) 이상을 감지하는가
- **전파 차단**: 감지된 오류가 다른 컴포넌트로 번지지 않도록 막는 경계 — 인터페이스 계약(`interface-contract.md`)의 오류 계약과 직결됨
- **안전 상태(safe state)**: 오류 발생 시 시스템이 전이하는 상태와 그 상태의 정의
- **독립성/간섭으로부터의 자유(freedom from interference)**: 서로 다른 ASIL(또는 ASIL과 QM)이 섞인 요소들이 공유 자원(메모리, 스케줄링, 통신 채널)을 통해 서로 영향을 주지 않는지. 공간적/시간적 분리(파티셔닝)가 필요한지, 아니면 ASIL 분해가 이미 적용되어 하위 요소 간 독립성이 요구되는지 확인하세요(요구사항 단계의 ASIL 분해 근거가 있다면 그대로 반영).

## 검증 관점에서 미리 확인할 것

ISO 26262는 아키텍처가 (1) 요구사항과 일관되는지, (2) 정의된 설계 원칙을 준수하는지, (3) 명명/설계 가이드라인을 따르는지, (4) 필요한 기능을 실제로 달성하는지를 검증하도록 요구합니다. 이 스킬의 SKILL.md 12단계(최종 자가 점검)는 이 네 가지를 미리 셀프 체크하려는 것입니다 — 나중에 리뷰에서 지적받을 것을 지금 스스로 잡아내세요.
