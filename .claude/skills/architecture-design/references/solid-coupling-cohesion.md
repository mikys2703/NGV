# SOLID, 응집도, 결합도 — 판단 기준

"응집력이 높다", "결합도가 낮다", "SOLID를 지켰다"는 선언이 아니라 아래 기준으로 실제 확인하는 항목입니다. 컴포넌트를 하나 그릴 때마다 이 체크리스트를 적용하세요.

## 결합도(Coupling) — 낮을수록 좋음, 순서대로 나쁨

| 유형 | 설명 | 이 스킬에서의 판정 |
|---|---|---|
| 내용 결합(Content) | 한 컴포넌트가 다른 컴포넌트의 내부 구현을 직접 수정/참조 | **금지** — 발견 즉시 재설계 |
| 공통 결합(Common) | 여러 컴포넌트가 전역 상태/공유 변수를 함께 사용 | **금지에 가까움** — 공유가 꼭 필요하면 별도 컴포넌트가 소유하고 인터페이스로만 접근하게 재구성 |
| 제어 결합(Control) | 한쪽이 다른 쪽에게 "무엇을 어떻게 할지" 플래그/모드로 지시 | 가능하면 피하고, 필요하면 인터페이스 계약에 그 제어 파라미터의 의미를 명확히 정의 |
| 스탬프 결합(Stamp) | 필요한 필드보다 큰 데이터 구조 전체를 인터페이스로 주고받음 | 인터페이스 크기 제한 원칙 위반 가능성 — 실제 필요한 필드만 노출하는 인터페이스로 축소 검토 |
| 데이터 결합(Data) | 필요한 데이터만 파라미터로 주고받음 | 목표 상태 |
| (메시지/이벤트 결합) | 이벤트·메시지로만 통신, 서로의 존재를 몰라도 됨 | 변경 용이성이 가장 높은 형태 — 이벤트 기반 아키텍처를 선택했다면 이 수준을 지향 |

컴포넌트 간 연결을 그릴 때마다 "이 연결이 표의 어느 줄에 해당하는가"를 스스로 답하세요. 내용/공통 결합이 나오면 그 설계는 응집도·결합도 요건을 충족하지 못한 것입니다.

## 응집도(Cohesion) — 높을수록 좋음, 순서대로 좋음

| 유형 | 설명 |
|---|---|
| 기능적 응집(Functional) | 컴포넌트의 모든 부분이 하나의 명확한 기능을 위해 함께 동작 — 목표 |
| 순차적 응집(Sequential) | 한 요소의 출력이 다음 요소의 입력이 되는 처리 파이프라인 — 양호 |
| 통신적 응집(Communicational) | 같은 데이터를 다루지만 서로 다른 기능 — 허용 가능하나 분리 검토 |
| 절차적/시간적/논리적/우연적 응집 | "그냥 같이 쓰여서", "초기화 시점이 같아서", "비슷한 종류라서" 묶인 경우 | **나쁨** — 나오면 컴포넌트를 목적 기준으로 다시 나누세요 |

컴포넌트 하나의 책임을 한 문장으로 설명할 수 없다면(그리고 그 이유가 "그리고"로 여러 개 이어진다면) 응집도가 낮다는 신호입니다.

## SOLID 원칙 — 아키텍처 수준에서의 의미

| 원칙 | 아키텍처 설계에서의 적용 |
|---|---|
| SRP (단일 책임) | 컴포넌트를 나눌 때 "이 컴포넌트가 바뀌어야 하는 이유가 하나뿐인가?"를 기준으로 경계를 긋습니다. 이유가 여러 개면 분리하세요. |
| OCP (개방-폐쇄) | 예상되는 변경 축(요구사항에서 "향후 옵션/변형"으로 명시된 부분)에 대해서는 인터페이스/확장점으로 열어두고, 그 외에는 억지로 확장 가능하게 만들지 마세요(불필요한 가변성은 오히려 ISO 26262 설계 원칙 위반). |
| LSP (리스코프 치환) | 같은 인터페이스를 구현하는 여러 컴포넌트(예: 대체 가능한 드라이버, 시뮬레이션용 스텁)가 서로 바꿔 끼워도 계약을 어기지 않아야 합니다 — 통합 순서(`integration-order.md`)의 스텁/드라이버 전략과 직결됩니다. |
| ISP (인터페이스 분리) | 인터페이스 하나에 서로 무관한 기능을 몰아넣지 마세요 — 사용하지 않는 메서드에 의존하게 만드는 인터페이스는 결합도를 높입니다. |
| DIP (의존성 역전) | 상위 수준 컴포넌트가 하위 수준의 구체 구현이 아니라 추상(인터페이스)에 의존하게 하세요 — `interface-contract.md`가 요구하는 "인터페이스로만 통신"의 근거가 이것입니다. |

## 점검 절차

논리 아키텍처를 그린 뒤, 컴포넌트마다 다음을 표로 만들어 확인하는 것을 권장합니다: `컴포넌트 | 책임(한 문장) | 응집도 유형 | 외부와의 결합 유형(연결마다) | SOLID 위반 여부`. 위반이 나오면 그 자리에서 구조를 조정하고, "알지만 이번엔 예외"로 넘어가야 한다면 그 이유를 템플릿 2장(아키텍처 설계 원칙) 또는 15장(참고자료/설계 결정 기록)에 명시적으로 남기세요 — 근거 없는 예외는 나중에 결함으로 취급됩니다.
