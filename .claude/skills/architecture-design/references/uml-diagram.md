# 아키텍처 다이어그램 — UML/SysML 표현

이 조직은 아키텍처 다이어그램을 draw.io(diagrams.net) 형식(`.drawio`)으로 관리합니다: `WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio`. Mermaid/PlantUML 텍스트 다이어그램이 아니라 이 형식을 기본으로 사용하세요(리뷰나 빠른 스케치 목적으로 Mermaid를 보조적으로 곁들이는 것은 무방하지만, 최종 산출물은 drawio 기준입니다).

## 실제 템플릿 구조

템플릿은 다음 요소로 구성됩니다 — 새 다이어그램도 이 뼈대를 그대로 재사용하세요.

- **시스템/설계 경계(boundary)**: 점선 사각형으로 작성 대상 범위를 표시
- **외부 액터/요소**: 경계 밖에 배치, 시스템과 상호작용하는 대상
- **대상 요소(element)**: 경계 안에 배치, "요소 ID + 요소 명칭"을 함께 표기
- **관계/인터페이스(edge)**: 요소 간 연결선에 관계 또는 인터페이스명을 라벨로 표기
- **작성 안내 박스**: 다이어그램에 반드시 담아야 할 4가지를 상기시킴
  1. 소프트웨어 요소와 계층
  2. 제공 및 요구 인터페이스
  3. 허용된 의존 방향
  4. 요구사항 할당 ID

## UML/SysML 표기 규칙

- **컴포넌트**: 사각형 박스, 상단에 요소 ID(예: `CMP-003`)와 명칭을 함께 표기. UML 컴포넌트 표기법(`«component»` 스테레오타입)을 쓸 수 있으면 사용하되, 이 조직 템플릿처럼 단순 박스+ID로도 충분합니다.
- **제공 인터페이스(provided interface)**: 볼(공 모양, lollipop) 표기 — 컴포넌트가 다른 컴포넌트에게 제공하는 기능.
- **요구 인터페이스(required interface)**: 소켓(반원) 표기 — 컴포넌트가 동작하기 위해 필요로 하는 기능. 제공-요구 소켓이 맞물리는 것이 "인터페이스로만 통신한다"를 그림으로 보여주는 방법입니다. draw.io 기본 UML 스텐실에 포함되어 있습니다.
- **의존 방향**: 화살표는 항상 "의존하는 쪽 → 의존받는 쪽"으로 그리고, 순환(사이클)이 생기면 `references/integration-order.md`의 순환 의존 점검에 걸립니다 — 발견 즉시 설계를 재검토하세요.
- **다이어그램 종류별 사용처**: 논리 아키텍처/컴포넌트 구조 → 컴포넌트 다이어그램(또는 SysML 블록 정의 다이어그램); 시나리오 호출 순서 → 시퀀스 다이어그램; 상태 의존 동작 → 상태 머신 다이어그램. 조직 템플릿은 이 세 종류를 한 파일에 페이지(탭)로 나눠 담는 방식을 허용합니다.

## drawio XML 생성 시 유의점

`.drawio` 파일은 XML(`mxGraphModel`)입니다. 새로 만들거나 템플릿을 채울 때:

- 템플릿의 `mxCell` 구조(`vertex`/`edge`, `style`, `geometry`)를 그대로 복제해 요소 수만 늘리세요 — 스타일을 임의로 바꾸면 조직의 다른 산출물과 시각적으로 어긋납니다.
- 각 요소 `value`에는 "요소 ID + 명칭"을, 각 관계 `value`에는 인터페이스명 또는 관계 종류를 넣으세요 — 빈 도형만 있는 다이어그램은 템플릿의 "작성 안내" 요구를 충족하지 못합니다.
- 완성 파일은 조직 명명 규칙에 따라 `ENG-SWE2-002_SW 아키텍처 UML 원본.drawio`로 저장하세요(경로는 `references/template.md`의 "완성된 산출물 경로" 참고).

## 다이어그램과 문서 본문의 일관성

다이어그램에 등장하는 요소 ID·인터페이스명은 본문 3~6장(논리 아키텍처/컴포넌트 책임/인터페이스 명세)의 표기와 **글자 그대로** 일치해야 합니다. 다이어그램에서는 `CMP-003`인데 본문 표에서는 "도어제어모듈"이라고만 쓰는 식의 불일치는 일관성 위반이며, 추적성도 끊어뜨립니다.
