## SWE.1과의 관계 — 유일한 테스트 베이시스

이 스킬의 테스트 베이시스는 **SW 요구사항 명세서**(`requirements-analysis` 스킬 산출물) 하나뿐입니다. 아키텍처 내부 구조나 구현 세부사항을 보고 케이스를 만들지 마세요(화이트박스 접근 금지) — 통합된 소프트웨어를 요구사항 기준으로 블랙박스 검증하는 것이 SWE.6의 정의입니다. 요구사항에 없는 내용을 명세서 대신 코드를 보고 추측하면 이 스킬을 따른 것이 아닙니다.

## SWE.4(단위검증)·SWE.5(통합시험)와의 경계 — 겹치지 않는 것

| 구분 | SWE.4 (`tdd`+`code-quality-gates`) | SWE.5 (`integration-testing`) | SWE.6 (이 스킬) |
|---|---|---|---|
| 테스트 베이시스 | 상세설계의 함수 계약/경계값/의사결정표 | 아키텍처의 인터페이스 계약·통합 순서 | SW 요구사항 명세서 |
| 검증 대상 | 함수/모듈 내부 로직 | 컴포넌트 간 인터페이스 상호작용 | 통합된 소프트웨어 전체의 대외 동작 |
| 접근 방식 | 화이트박스 | 그레이박스(인터페이스 계약 기준) | 블랙박스 |
| 산출물 | Python `unittest` 코드 | `TPL-SWE5-001/002/003` | `TPL-SWE6-001/002` |
| ISO 26262-6 절 | Clause 8(설계)/9(단위검증) | Clause 10(통합) | Clause 11(SW 안전요구사항 검증) |

같은 결함이 여러 수준에서 발견될 수는 있지만(예: 경계값 오류가 단위시험과 시스템시험 모두에서 드러남), 이 스킬이 함수 내부 분기나 컴포넌트 간 인터페이스 계약을 직접 검증하려 하지 마세요 — 그 결과는 각각 SWE.4/SWE.5 산출물의 몫이며, 이 스킬은 "요구사항대로 동작하는가"만 봅니다. 반대로 요구사항 명세서에 없는 내부 구조 문제를 발견했다면, 이 스킬의 결과서(TPL-SWE6-002)에 기록하되 원인 분석은 해당 수준의 스킬로 넘기세요.
